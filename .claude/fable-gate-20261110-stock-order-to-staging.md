# Fable 게이트 판정 — 재고 화면 발주 = «발주 대기에 담기» (2026-11-10)

설계: `.claude/fable-design-20261110-stock-order-to-staging.md` · 팀원 증거: `.claude/verify-evidence-20261110-stock-order-to-staging.md`

## 판정: **PASS (개발서버 완료)** — 운영 배포 전 조건 2개(맨 아래)

Irene 원문 «스톡에서 발주하면 바로 발주되면 안돼. PO로 보내야 하는 거 아니야? 그리고 스톡에서 보냈다고 알게도 확인하고.» 의 두 요구가 모두 충족됐다.
- **바로 안 나간다**: 재고 화면 두 길(단건·일괄) 모두 `bulk {source:'stock'}` 만 부르고 `auto_submit` 을 보내지 않는다. 화면 소스 전체에서 `auto_submit` 을 보내는 곳은 `NewPurchaseOrderPage` 의 `false` 하나뿐. 판매자·오너 통지와 상태 변경은 서버 `auto_submit` 분기 안에만 있고, 초안 만들기 함수(`createPurchaseOrderCore`)에는 통지 호출이 없다.
- **재고에서 담았다고 알 수 있다**: 초안 진행 기록에 `source:'stock'` 한 건(누가·언제·품목·수량)이 같은 트랜잭션에서 남고, 발주 대기 줄에 «From Stock» 꼬리표, 재고 목록에 «In Pending POs · n» 링크, 발주 상세 타임라인에 품목·수량이 붙는다.

## 내가 직접 한 것 (Fable 직접)
1. **diff 대조(설계 범위)** — 서버 3파일 + health-check + 화면 9파일 + 번역 8파일. 
   - `classify`·`on_order`·`suggested_*`·summary 계산: 변경 0(표시용 두 칸 `in_staging`·`in_staging_order_qty` 만 추가). `stagingQty`/`stagingQtyBrand` 는 `onOrderQty`/`onOrderQtyBrand` 와 같은 범위 조건·상태만 `draft`.
   - 서버 `auto_submit` 분기 무변경. `source` 는 `'stock'` 만 인정.
   - `consolidate-drafts`: 지워지는 초안의 재고 기록만 남는 초안으로 옮김(시각 순).
   - 판매자 타임라인은 `buyer_only` 기록을 그리지 않음. 타임라인 단계 계산은 `draft` 상태 기록에 영향받지 않음(단계 목록에 없는 상태 — 메모 줄로만 나옴).
   - 새 DB 칸·ENUM·마이그 0. 정기 발주·카트·새 발주 화면 무접촉.
2. **재실행** — `health-check --grep="재고 화면 발주"` 1/1 통과(K1 초안 유지·판매자 목록에 없음 / K2 기록 1건→두 번 담기 줄 1·수량 5·기록 2 / K3 발주 대기 수량 5, 상태·오는 중 불변). 잔재 0.
3. **가드** — `check-print-guard` 8/8 변경 없음. 4개 언어 `toStaging` 15키·`staging.fromStock*` 존재 확인.
4. **verify-all --full 2차(최종 번들)** 끝까지 확인 — **23/24**. health-check 전체 회귀 통과 · 인쇄 라우트 가드 통과 · 타입 기준선 신규 0 · i18n 일치 · 디자인/타임존 신규 0 · 번들 신선도 통과 · 실브라우저 mount sweep 크래시 0(764.7초). 실패 1건 = `deploy-ready`(배포 기록 파일 없음 · SW 버전 그대로) — 배포 때 채우는 항목이라 이번 판정을 막지 않는다.

## 설계와 다른 점 — 판단
- **문구 «Order Staging» → «Pending POs / 발주 대기»**: 수용. 같은 화면을 두 이름으로 부르지 않는 쪽이 맞다.
- **설계 밖 1건(재고 목록 행 «Order» 버튼이 `min_order` «0.00» 글자를 읽어 눌러도 아무 일 없던 것)**: 수용. 이 버튼이 이번 흐름의 입구라 안 고치면 «담기» 자체가 안 된다. 칸에 보이는 수량을 그대로 쓰게 한 것이고 서버·계산 무변경.
- **고장주입 자리**: 설계는 화면 훅에 `auto_submit` 을 되살리는 것이었고 팀원은 서버에서 되살렸다. K1 이 «바로 나감» 을 잡는다는 반증으로는 유효(실패 → 원복 → 통과). 다만 이 검사는 **서버 계약**을 지키는 것이고, 화면이 다시 `auto_submit:true` 를 보내는 회귀는 이 검사가 못 잡는다 — 지금은 소스 검색으로 0건임을 확인했다.

## 확인 못 한 것 (추측하지 않음)
- 발주 대기에서 **Submit 한 뒤** 그 발주 상세·오너 승인 화면 타임라인에 «Added from Stock — 품목 × 수량» 이 실제로 보이는지: 브라우저로 보지 않았다. 근거는 코드뿐 — 제출이 쓰는 기록 함수는 기존 기록을 복사해 덧붙이고(K2 에서 덧붙임 보존은 실증됨), 상세 화면은 기록 전체를 그린다.
- Submit 뒤 `in_staging` 0 · `on_order` 증가(설계 §4-5 뒷부분): 실호출 안 함. 쿼리 조건(초안만 / 받을 수 있는 상태만)으로만 판단.
- 일괄 창 실브라우저 클릭, «필요한 것 담기» 연속 두 번(§4-6): 팀원·나 모두 브라우저로 안 함. 기본 수량 빼기·«이미 담김» 묶음은 코드로만 확인.
- 담기 때 메일·소켓 0건을 로그로 보지는 않았다(코드상 호출 자리가 `auto_submit` 분기뿐).
- 판매자 **API 응답**에는 제출 뒤 `buyer_only` 기록이 그대로 실려 간다(화면만 거른다). 설계가 정한 대로이고 비밀 정보는 아니다(담은 사람 이름·수량).

## 알고 넘어가는 한계 (후속 필요 없음, 기록만)
- 발주 대기에서 재고로 담은 줄을 지운 뒤 같은 품목을 카트로 다시 담으면 «From Stock» 꼬리표가 붙는다(기록은 «그때 담았다» 는 사실이라 지워지지 않음).
- 오너 승인 대기 중인 발주는 «발주 대기» 에도 «오는 중» 에도 안 잡힌다 — 기존 동작, 설계 §3 에서 범위 밖으로 둠.

## 운영 배포 전 조건
1. **SW 버전 올리기 + 배포 기록 파일**(`deploy-ready` 가 막는 2건). 화면이 바뀌었으므로 SW 를 안 올리면 매장 브라우저가 옛 «바로 보내기» 번들을 계속 쓴다 — 이번 건은 그게 곧 Irene 이 지적한 동작이라 꼭 올린다.
2. 민감 판정 목록의 다른 파일들(청구서·구독·마이그·POSTerminal 등)은 이미 커밋된 앞선 작업분이며 이번 판정 범위가 아니다. 이번 판정은 위 diff 범위에 한한다.

통과 마커: 이 문서를 쓴 직후 `fable-gate.js pass` 실행(이 파일도 지문에 들어가므로 순서를 이렇게 둠).
