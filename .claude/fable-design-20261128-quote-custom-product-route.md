## Irene 원문 (2026-11-28)

«견적문의받은 후 상품등록해서 견적상품 판매하는 루트도 만들자. 지금 있는 형태에서 모두 그래도 기능 사용하면서 UI/UX에서 알기 쉽게 할 수 있을까? 발주하는 곳에서 디자인 의뢰를 할 수 있게 별도로 표시 하는 거야. 그리고 그 디자인의뢰는 파트너로 등록되어 있는 업체 것은 따로 표시가 되어서 하는 거야. 이건 공급업체들이 제공하게 하는게 낫겠지? 브랜드제너럴은 브랜드에게만 대응하는 것으로 분리하고. 같은 회사라고 해도 말이야. 아니면 브랜드제너럴이 그냥 모든 업체게 제공하는 서비스도 열어도 될까? 구조 좀 파악해봐. 커스터마이징 제품들을 레스토랑들에게 판매해 나갈 기반을 마련하고 싶어. 이걸 플랫폼 자체 구조로 가면 이상하니까 공급업체 기준으로 두고 플랫폼 운영사여도 이 사업루트는 그 역할로 운영하는 게 맞겠지? fable이 전체 검토 좀 해줘.»

## 0. 한 줄 결론

**할 수 있다. 뒤쪽 절반(상품 → 발주 → 준비 → 배송 → 청구 → 결제)은 지금 것을 그대로 쓰고, 앞쪽 절반(의뢰 받기 · 그 손님 전용 상품)만 새로 붙인다.**
새 주문 표·새 견적 금액 문서·새 역할은 만들지 않는다. «견적» = 판매자가 그 손님 전용으로 등록한 상품(가격·최소 수량·납기)이고, «수락» = 그 상품이 손님 발주 목록에 담기는 것이다. 그 뒤는 평소 발주와 똑같다.

Irene 의 방향 세 가지는 모두 구조에 맞다 — ① 공급업체 기준 ② 브랜드 제너럴은 자기 브랜드(가맹점)에만 ③ 플랫폼 운영사도 «공급업체 역할» 로 운영.

## 1. 실측 — 지금 되는 것 · 안 되는 것

| 필요한 것 | 브랜드 제너럴(판매자) | 공급업체(판매자) | 근거 |
|---|---|---|---|
| 주문제작 상품(재고 안 셈 · 배송 함) | **있음** | **없음** | `brand_products.product_kind` 3값 / `supplier_products` 에는 칸 없음 |
| 서비스 상품(배송 없음 · 완료 처리 — 디자인 작업비) | **있음** | **없음** | `utils/orderFulfillment.js` 가 브랜드 상품만 본다 |
| 특정 손님에게만 보이는 상품 | **있음** (`specific_restaurants`) | **없음** | `routes/supplier-directory.js:656~` 계약·열림 업체의 활성 상품 **전부**가 모든 거래처에 보인다 |
| 출고 때 재고 | 주문제작은 안 깎음 | **무조건 깎음** → 주문제작이면 재고가 마이너스 | `routes/seller-orders.js:853` |
| 판매자가 손님 대신 주문 넣기 | 있음 | 있음(연결된 상품만) | `routes/seller-orders.js:1368~` |
| 발주·준비 보드·배송·청구서·결제·반품·정기 발주 | 있음 | 있음 | 기존 그대로 |
| 손님 → 판매자 «의뢰·문의» 받는 자리 | 없음 | 없음 | 계약 신청의 한 줄 메시지뿐 |
| 의뢰에 파일(로고·시안) 붙이기 | 없음 | 없음 | 발주에는 인보이스·영수증 파일 칸만 |
| «파트너 업체» 표시 | 없음 | 없음 | «Partner» 는 추천인(소개 수수료) 역할에만 쓰는 말 |
| 판매자가 «누구나 주문 가능 / 계약 필요» 고르기 | 있음 | 있음 | `utils/salesAccess.js` |

**여기서 나오는 사실 두 가지**
1. **GIT 같은 브랜드 제너럴 → 자기 가맹점** 맞춤 상품 판매는 **오늘도 코드 변경 없이 된다**(문의만 전화·왓츠앱으로 받고, 상품을 «주문제작 + 그 매장에만» 으로 등록). 빠진 것은 «의뢰를 시스템 안에서 받는 자리» 뿐이다.
2. **공급업체는 지금 안 된다.** A 식당 로고 컵을 등록하면 그 공급업체의 **모든 거래처에 보이고**, 보낼 때마다 재고가 마이너스로 내려간다. 이 사업의 기준을 공급업체로 두려면 여기가 먼저다.

## 2. Irene 질문별 판정

### 2-1. «지금 있는 형태에서 기능 그대로 쓰면서 알기 쉽게 할 수 있나» → 된다

흐름(손님 눈):
1. 발주 화면에 **«맞춤 제작 의뢰»** 입구 → 업체 고르고, 무엇을·몇 개·언제까지 + 로고/참고 파일 올려 보냄.
2. 판매자가 대화로 시안·질문을 주고받다가 **«견적 상품 만들기»** — 평소 쓰던 상품 등록 창이 «이 손님 전용 · 주문제작» 으로 미리 채워져 열린다. 가격·최소 수량·납기를 넣고 보냄.
3. 손님이 의뢰 화면에서 견적을 보고 **«수락하고 발주에 담기»** → 평소 발주 대기 목록에 들어감. 여기부터는 지금 발주와 100% 같다(오너 승인·결제·배송·수령·청구서).
4. **재주문은 그냥 평소 발주** — 그 상품이 손님 목록에 «전용 상품» 표시와 함께 계속 남아 있다. 맞춤 상품 사업의 진짜 매출은 재주문이라 이 점이 핵심이다.

### 2-2. «발주하는 곳에서 디자인 의뢰 별도 표시» → 한다. 이름은 넓게

- 입구는 발주 화면 한 곳. 의뢰를 받겠다고 **켠 판매자만** 나온다(판매자 설정에 스위치 하나 — 새 칸 없이 기존 판매자 설정 묶음에 넣는다. «누구나 주문 가능» 스위치와 같은 방식).
- 이름을 «디자인 의뢰» 로 좁히면 로고 인쇄물만 담긴다. Irene 목표(«커스터마이징 제품들»)에는 전용 소스·유니폼·간판·맞춤 포장도 들어가므로 **«맞춤 제작 의뢰»** 로 두고, 그 안에서 종류(디자인·인쇄 / 식품 맞춤 / 기타)를 고르게 하는 쪽이 맞다.

### 2-3. «파트너로 등록된 업체는 따로 표시» → 한다. 단 두 가지 주의

- **누가 붙이는가**: 업체가 스스로 켤 수 있으면 표시의 뜻이 없다. **시스템 관리자만** 붙이는 표시로 둔다(업체 회사 정보에 칸 하나 · 업체 본인 설정 화면에서는 못 바꿈).
- **말이 겹친다**: «Partner» 는 이미 추천인(소개 수수료) 역할 이름이다. 화면 글자는 **«공식 파트너 / Official Partner»** 처럼 구분되는 말로.
- 표시 방식: 의뢰 입구에서 공식 파트너를 **맨 위 묶음 + 배지**로, 나머지 업체는 그 아래.

### 2-4. «공급업체가 제공하는 게 낫겠지?» → 맞다

공급업체는 매장·브랜드·푸드코트·오너 누구와도 계약(또는 «누구나 주문 가능»)으로 거래하는 구조가 이미 있다. 맞춤 제작을 여러 식당에 팔아 나가는 사업의 그릇으로 맞다. 다만 §1 의 빈 칸 셋(주문제작 종류 · 전용 상품 · 의뢰함)을 공급업체 쪽에 채워야 한다.

### 2-5. «브랜드 제너럴은 브랜드에만 / 아니면 모든 업체에 열까» → 1단계는 자기 가맹점에만

- 브랜드 제너럴 판매 흐름에는 «본부–가맹점» 전제가 깊이 들어 있다 — 오너 승인, 직영점은 결제 불필요, 월 정산서, 브랜드 재고 공유. 바깥 손님이 맞춤 주문으로 섞이면 돈 규칙이 손님마다 갈린다.
- 같은 회사가 «브랜드 본부» 와 «공급업체» 두 얼굴로 같은 손님에게 보이면, 전에 겪은 «같은 물건이 두 상품» 사고가 다시 난다.
- **되돌리기 방향**: 닫아 두었다가 나중에 여는 것은 스위치 하나다. 열었다가 닫는 것은 이미 생긴 거래·청구서 때문에 어렵다. 그래서 닫은 쪽에서 시작한다.
- 같은 회사가 바깥에도 팔고 싶으면 **공급업체 계정을 하나 더 두고 그 역할로** 판다(Irene 말 그대로 «같은 회사라고 해도 분리»).
- 참고: 브랜드 제너럴의 **기성 상품**을 바깥 구매자에게 파는 문(«다른 구매자에게도 판매»)은 이미 있고 이번에 닫지 않는다. 이번 판정은 «맞춤 제작 의뢰 입구» 에만 해당한다.

### 2-6. «플랫폼 운영사도 공급업체 역할로 운영하는 게 맞겠지?» → 맞다

- 시스템 관리자는 모든 매장을 보는 역할이다. 그 자리가 판매자가 되면 권한·청구서 발행자·장부가 섞인다(플랫폼 이용료 청구와 상품 판매 청구는 다른 장부여야 한다).
- 운영사는 **공급업체 회사 하나를 만들어** 그 계정으로 상품·의뢰·주문·청구를 운영한다. 다른 공급업체와 **같은 화면·같은 규칙**을 쓰게 되어, 우리가 먼저 써 보며 고치는 효과도 있다.
- 지금 플랫폼 구조 안에 있는 «하드웨어 견적»(시스템 관리자 화면)은 이번에 건드리지 않는다. 나중에 이 공급업체 역할로 옮길 후보로만 적어 둔다.

## 3. 설계 방향 — 무엇을 그대로 쓰고 무엇이 새로 필요한가

### 그대로 쓰는 것 (새로 만들지 않음)
- 발주·발주 대기·오너 승인·준비 보드·배송·수령·반품·청구서·결제·정기 발주 — 전부.
- 계약/열림 판정(`salesAccess`) · 카탈로그 담기 · 판매자 대신 주문.
- 브랜드 제너럴의 주문제작·서비스 종류와 «특정 매장에만» 배포.
- 대화 = 기존 댓글 기능(종류 값 하나 추가 — 값은 늘리기만).
- 파일 = 기존 이미지·파일 저장 규칙.
- 판매자 설정 = 기존 설정 묶음에 키 하나.

### 기각한 길 (다시 꺼내지 않게)
- **견적 금액 문서를 따로 만들기** — 돈이 사는 곳이 발주·청구서 말고 하나 더 생긴다. 견적 = 전용 상품의 가격이다.
- **하드웨어 견적 표 재사용** — 그건 «플랫폼이 비로그인 손님에게» 보내는 것이라 주체가 다르다. 얹으면 플랫폼 구조로 끌려간다(Irene 이 피하려는 것).
- **매장↔브랜드 운영 문의에 얹기** — 일정·직원·메뉴 문의용이고 공급업체는 받는 쪽이 아니다. 견적 상품·상태를 붙이면 두 개념이 섞인다.
- **상품 없이 발주에 자유 줄 넣기** — 발주 줄은 «넷 중 하나를 가리킨다» 가 불변이다(2026-10-01 판정과 같음).
- **새 역할(디자인 업체 등)** — 공급업체 역할 그대로.
- **일반 소비자 판매** — 2026-09-12 보류 그대로. 이 루트는 사업자 간 거래다.

### 단계
- **1단계 — 공급업체에 빈 칸 채우기 (N1 · N2).** 이것만으로 «문의는 전화·왓츠앱 → 전용 상품 등록 → 손님이 평소처럼 발주» 가 공급업체에서도 된다. 가장 작고, 이후 단계가 전부 이 위에 선다. DB 칸 추가 + 보안 경계라 끝나면 Fable 검증 1회.
- **2단계 — 의뢰함 (N3 · N4 · N5 · N7 · N8).** 발주 화면의 «맞춤 제작 의뢰» 입구와 판매자 의뢰함. 브랜드 제너럴(가맹점 대상)과 공급업체가 **같은 화면·같은 표**를 쓴다. 화면 설계 먼저.
- **3단계 — 공식 파트너 표시 (N6) + 운영사 공급업체 계정 개설**(계정 만들기는 코드가 아니라 운영 작업).
- **나중 후보** — 견적서 PDF 출력 · 시안 «확정» 단계 분리 · 브랜드 제너럴 맞춤 의뢰 바깥 개방 · 하드웨어 견적을 공급업체 역할로 이전.

구현 전에 `docs/TRADE_STRUCTURE.md` 에 «맞춤 제작 루트» 절을 먼저 적는다(판매자 = 공급업체 기준 · 견적 = 전용 상품 · 새 금액 문서 없음 · 전용 상품 판정은 한 곳).

## 4. Irene 가 정할 것 (Fable 권고 붙임)

1. **브랜드 제너럴의 맞춤 제작 의뢰를 어디까지 받게 할까요?**
   - (가) 자기 브랜드 가맹점에만 — **Fable 권고.** 나중에 여는 것은 쉽고, 열었다 닫기는 어렵다.
   - (나) 모든 업체에 — 본부–가맹점 돈 규칙(승인·정산서·직영점)에 바깥 손님이 섞여 규칙이 갈린다. 바깥에 팔 회사는 공급업체 계정을 따로 두면 같은 결과를 얻는다.
2. **입구 이름을 무엇으로 할까요?**
   - (가) «맞춤 제작 의뢰» + 안에서 종류 선택(디자인·인쇄 / 식품 맞춤 / 기타) — **Fable 권고.** «커스터마이징 제품들» 전체가 담긴다.
   - (나) «디자인 의뢰» — 알기 쉽지만 로고·인쇄물 밖의 맞춤 상품이 들어갈 자리가 없다.
3. **«공식 파트너» 표시는 누가 붙일까요?**
   - (가) 시스템 관리자가 직접 지정 — **Fable 권고.** 표시의 신뢰가 유지되고 구현이 가장 작다.
   - (나) 조건 자동(거래 건수 등) — 기준을 정하고 계산·예외를 관리해야 한다. 업체 수가 적은 지금은 이르다.
4. **어디부터 만들까요?**
   - (가) 1단계(공급업체 전용 상품·주문제작)부터, 그다음 의뢰함 — **Fable 권고.** 작게 끝나고 바로 쓸 수 있으며, 의뢰함이 그 위에 선다.
   - (나) 1~3단계를 한 번에 — 화면까지 한꺼번에 나오지만 검증 범위가 크고(권한·DB·새 화면 동시) 오래 걸린다.

## 5. 확인 못 한 것

- 운영에 플랫폼 운영사가 판매자로 등록된 사례가 있는지(운영 DB 를 읽지 않음).
- 한 로그인 계정이 «브랜드 제너럴» 과 «공급업체 관리자» 를 함께 가질 수 있는지 — 안 되면 운영사·GIT 는 공급업체용 계정(이메일)을 따로 둔다. 1단계 설계 때 실측한다.
- 공급업체 상품을 읽는 자리의 전체 목록(N2 의 «보이는 곳 전부») — 방향만 정했고, 1단계 기술 설계에서 전수 조사한다.
- 화면 배치(입구 위치·의뢰함 모양)는 이번 판정 범위 밖 — 2단계 화면 설계에서 정한다.
