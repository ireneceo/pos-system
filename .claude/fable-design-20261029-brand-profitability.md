## 2. 구조 — 세 층·세 역할

기획 글의 «세 단계를 분리» 를 우리 구조에 그대로 앉힌다.

```
① 메뉴 이론 수익성  = 판매 라인 × (지금 레시피 원가 + 옵션·구성품 원가) − 주문별 변동비   ← POS 자동
② 매장 실제 손익    = 순매출 − 실제 식재료비(장부) − 인건비(출퇴근×시급) − 운영비(규칙) − 수수료   ← 매장 입력 최소 4가지
③ 이론 vs 실제      = 재료별 (기초+매입−기말) − 판매 차감 − 설명되는 사용(폐기·만들기·조정)      ← 이미 있음(foodCostMath)
```

| 역할 | 보는 범위 | 보는 것 | 근거 |
|---|---|---|---|
| **Restaurant Admin** | 자기 매장 1 | ①②③ 전부 + 설정(시급·운영비·수수료·공유 스위치) | 현장 운영자 |
| **Restaurant Owner** | 소유 매장 N | 매장마다 ①②③ 전부 + **매장 비교** | 재무/통계 역할(`RESTAURANT_OWNER_PLAN`) — 공유 스위치도 Owner 가 켤 수 있다 |
| **Brand General** | 브랜드 매장 N(소유∪배정) | 매장마다 ①③ + ② 는 매장이 공유를 켠 것만(Q1) + **가맹점 비교** + **표준 원가 vs 매장 원가** + 브랜드 자체 판매 마진(이미 있는 `productMargin`) | 본사 |
| **Brand Manager** | 맡은 브랜드 | BG 와 같되 돈 칸은 기존 규칙대로 가림(`financial_redacted`) | 2026-10-11 판정 그대로 |
| Staff | — | 못 봄 | 원가 = 관리 정보 |

**계산은 한 곳.** `services/profitability/` 아래 매장 1개 × 기간 1개를 받는 함수 묶음(`storeMenuContribution` · `storePnl` · `storeVariance` · `storeOrderMix` · `storeSimBaseline`)을 만들고, 매장·오너·브랜드 라우트가 **같은 함수를 호출**한다. 오너·브랜드는 매장 id 목록만 다르다. 지금 오너·브랜드 화면처럼 브라우저가 주문을 세는 길은 만들지 않는다.

## 3. 계산 정의 (calc) — 단일 소스 `utils/profitabilityMath.js`(순수 함수) + 검산 사례

### 3-1. 메뉴 1인분 이론 원가 — `menuUnitCosts` 를 **확장**(새 식 아님)
- 본체 = 지금 그대로(레시피 Σ줄원가 / 재료 직결 / 상품 자체 unit_cost). 줄 하나라도 모르면 null.
- **+ 옵션**: 라인의 `selectedOptions[].id` → `option_ingredients` × 수량 → `computeLineCost`. 옵션 재료 연결이 없으면 옵션 원가 0 이 아니라 **«옵션 원가 미등록»** 으로 표시만 하고 본체 원가는 그대로(옵션은 대개 소액이라 메뉴 전체를 null 로 만들지 않는다).
- **+ 세트 구성품**: `set_components[].product_id`(숫자) 각각의 본체 원가 × qty. 구성품 하나라도 모르면 세트 원가 null. 표시용 `set_items` 는 읽지 않는다(메모리 규칙).
- 어느 시점 원가인가 — **두 눈금을 둔다**, 섞지 않는다:
  - «지금 레시피 기준»(현재 원가) — 메뉴 성과판·시뮬레이터용. 화면 라벨 «현재 레시피 기준».
  - «판매 시점 기준» — 재고 장부 `order_deduct.cost_value` 를 `order_id` 로 묶은 값. 기간 손익·이론 vs 실제용. 라벨 «판매 당시 원가».
  장부가 없는 라인(차감 안 된 주문·레시피 없던 시절)은 현재 기준으로 채우고 **«추정» 건수를 센다**(숨기지 않는다 — foodCostReport 의 `unknown_rows` 와 같은 태도).

### 3-2. 주문·라인 금액 — 매출 정의는 `revenueOrderWhere` 그대로 + 제외 2가지
- 대상 주문 = `status IN (completed, served)` AND 삭제 아님(기존 단일 정의) **AND `payment_method <> 'staffMeal'`**(직원 식사는 매출이 아니라 비용) — 수익성 계산에서만 뺀다. 기존 매출 화면은 건드리지 않는다(바꾸려면 별건).
- 주문 순매출 `net_sales` = `subtotal + takeaway_charge − discount − discount_policy_amount − coupon_discount − point_discount` (= orderTotals 의 afterDiscount). **세금·서비스차지·배달요금 제외.**
- 서비스차지·배달요금은 **«기타 수입»** 줄로 따로(서비스차지는 매장 수입이지만 메뉴 가격이 아니라 공헌이익률 분모에 넣지 않는다).
- 라인 순매출 = `line.total` × (주문 net_sales ÷ 주문 (subtotal+takeaway_charge)) — 주문 할인을 라인에 비례 배분. 할인 100 % 주문(서비스 제공)은 라인 매출 0, 원가는 그대로 → 자동으로 «공짜로 나간 원가» 가 된다.
- 주문별 변동비 `order_fee` = net_sales × 그 주문 결제수단의 수수료 %(§4-2) + 채널 수수료 %(delivery/pickup 등 설정이 있으면). 라인엔 같은 비율로 배분.
- **공헌이익** = 라인 순매출 − 라인 원가 − 라인 수수료 · **공헌이익률** = 공헌이익 ÷ 라인 순매출(매출 0 이면 null).
- 원가 모르는 라인은 공헌이익 null → 집계는 **아는 라인만** 더하고 «원가 아는 매출 비중 %» 를 함께 돌려준다(카테고리 원가율이 이미 이렇게 한다).

### 3-3. 매장 손익(기간) — waterfall 한 줄
```
총매출(주문 subtotal+포장요금 합)
− 할인(4종 합)                       = 순매출 S
− 실제 식재료비 F_act (장부: 기초+매입−기말, foodCostMath.actual_usage)   ← 재고 모듈 있을 때
   (없으면 이론 식재료비 F_theo = Σ 판매 당시 원가, 라벨 «이론»)
− 결제·채널 수수료 (§3-2 order_fee 합)
= 공헌이익 (매장)
− 인건비 L (§3-4)
= 프라임코스트 뒤 이익      (프라임코스트 = F + L · 프라임코스트율 = (F+L)/S)
− 임대료 rent(S) (§3-5)
− 로열티·마케팅비 (순매출 % 규칙)
− 공과금·기타 고정 운영비 (월 금액 규칙 또는 그 달 입력값)
− 외부 채널 수수료 (Q3-A: 외부 월매출 × %)   (+ 외부 채널 월매출은 총매출 위에 별도 줄로 더함)
+ 기타 수입 (서비스차지·배달요금 수입)
= 영업이익 (추정)
```
- 기간은 매장 타임존 `getDateBounds` 한 곳. 월 규칙은 기간 일수 비례(«10월 1~15일» 이면 월 임대료 × 15/31).
- 식재료비는 **장부 값이 있으면 장부, 없으면 이론** — 어느 쪽인지 라벨에 박는다. 둘 다 있으면 둘 다 보여 주고 차이가 §3-6.
- 브랜드 물건 매입(브랜드 SOA)은 발주 수령으로 이미 `purchase` 장부에 있다 → **운영비에 «브랜드 매입» 항목을 두지 않는다**(이중 계상 차단 — 운영비 카테고리에 그런 값이 없다).

### 3-4. 인건비
- 시간제: `attendance_records`(closed·corrected, 기간 안 `work_date`) 의 (clock_out − clock_in) 시간 × `staff_work_profiles.hourly_rate`. 열린 기록(미퇴근)은 제외하고 건수만 «미퇴근 n건» 으로.
- 월급제: `monthly_salary` × (기간 일수 ÷ 그 달 일수). 출퇴근을 안 찍어도 들어간다.
- 시급·급여 둘 다 없는 직원은 «단가 없음» 으로 빠지고 인원 수를 센다(0 으로 넣지 않는다).
- **시간대별 인건비**: 각 근무 기록을 걸친 시(時) 마다 분 단위로 쪼개 시급을 배분 → 시간대별 매출(`hourlySales`)과 나란히 → **시간대 인건비율** = 그 시간 인건비 ÷ 그 시간 순매출(매출 0 이면 null, «손님 없음» 으로 표시).
- **직원 1시간당 매출** = 순매출 ÷ Σ근무시간(시간제+월급제 모두의 출퇴근 시간; 출퇴근 없는 월급제는 분모에서 빠지고 표시 «출퇴근 기록 없는 직원 n명»).
- 급여 세부(EPF·SOCSO·수당)는 비범위 — 기획 글대로 «나라마다 달라서» 다음.

### 3-5. 임대료 규칙 (기획 글 «RM6,000 과 매출 13 % 중 높은 금액»)
- 규칙 3종: `fixed`(월 R0) · `pct`(순매출 × r) · `max`(max(R0, r·S)). 입력은 §4-2 운영비 표.
- 임대인이 PurpleHere 푸드코트인 매장은 계약 `financial_terms` 에서 **읽기만**(base_rent → R0, revenue_share_percent → r, 둘 다 있으면 max). 운영비 표에 행이 있으면 그 행이 이긴다(매장이 아는 숫자가 정본).
- 분모 S 는 순매출(§3-2). 몰 GTO 가 «세전·할인후·서비스차지 포함»(IOI 사례) 처럼 다르면 **기간 손익엔 영향이 작아** 1단계는 순매출로 통일하고 라벨에 «GTO 기준은 몰 계약서 확인» 한 줄.

### 3-6. 이론 vs 실제(재료별) — `foodCostMath.ingredientPeriod` 그대로 + **수량** 눈금 추가
- 지금은 금액만 돌려준다. 기획 글의 «닭고기 100 kg 이어야 하는데 112 kg» 은 **수량** 이라, 같은 장부 줄에서 `quantity_change` 합도 같이 뽑는다(기초·기말 수량은 이미 서비스가 계산한다).
- 재료 한 줄 = 이론 사용량(order_deduct) · 실제 사용량(기초+매입−기말) · 차이량·차이 % · 설명되는 사용(폐기 사유별·만들기·조정) · 설명 안 되는 차이(실사 차이 = 원인 모름) · 금액.
- 판정 색: 차이 % 가 설정 임계(기본 ±10 %) 밖이면 주의. 이론 0 인데 실제 > 0 이면 «레시피에 없는 재료가 나감 — 레시피 연결 확인» 으로 따로 묶는다(차이율 ∞ 로 그리지 않는다).

### 3-7. 메뉴 성과판(4분면)
- x = 판매량(기간 수량) · y = 1개당 공헌이익(원가 아는 메뉴만). 각 축 기준선 = **매출 가중 평균이 아니라 메뉴 수 기준 중앙값**(소수 대표 메뉴가 기준을 끌어올리지 않게; Menu Engineering 표준은 평균의 70 % 를 쓰지만 우리는 메뉴 수가 적은 매장이 많아 중앙값이 안정적) — 설정에서 «평균 70 %» 로 바꿀 수 있게 상수만 분리.
- 4분면 이름(화면 문구, 영어 기본): Stars(많이 팔리고 많이 남음) · Plowhorses(많이 팔리나 적게 남음) · Puzzles(적게 팔리나 많이 남음) · Dogs(둘 다 낮음). 각 분면에 기획 글의 행동 문구 1줄.
- 원가 모르는 메뉴는 분면 밖 «원가 미등록» 열에 따로(지우지 않는다 — 여기가 «레시피 걸어라» 의 입구).

### 3-8. 주문 구성
- 객단가 = 순매출 ÷ 주문 수 · 주문당 공헌이익 = Σ라인 공헌이익 ÷ 주문 수(원가 아는 라인만, 비중 표시).
- **동반주문률(카테고리별)** = 그 카테고리 품목이 1개 이상 든 주문 수 ÷ 전체 주문 수 — «사이드·밥·음료 추가율» 을 매장 설정 없이 **모든 카테고리에 대해** 낸다(어느 카테고리가 사이드인지 매장이 고르게 하지 않는다 — 입력 0).
- **옵션 추가율** = 유료 옵션(`selectedOptions[].price > 0`) 이 붙은 라인 수 ÷ 라인 수(«토핑 추가율» 자리).
- **세트 전환율** = 세트 라인(`is_set_menu` 또는 `set_components` 있음) 이 든 주문 ÷ 전체 주문.
- **채널별** = `order_type × source` 9칸 중 있는 것만: 주문 수·순매출·객단가·주문당 공헌이익·수수료.
- **조합** = 같은 주문에 함께 든 메뉴 쌍 상위 10(지지도 = 함께 든 주문 수 ÷ 전체). 쌍의 공헌이익 합을 옆에.

### 3-9. 손익 시뮬레이터 v1 — 브라우저 순수 계산(저장 없음), 기준값은 서버가 준다
- 기준값(최근 8~12주 실적에서): 평균 공헌이익률 c(원가 아는 라인), 채널 비중, 객단가 A, 일평균 주문 수, 월 인건비 L, 운영비 규칙(임대·로열티·기타), 수수료율, 외부 채널.
- 조정 손잡이(기획 글 10개 그대로): 월매출 S · 메뉴 판매비중(상위 10 메뉴 슬라이더, 나머지 «기타») · 채널 비중 · 할인율 d · 평균 폐기율 w · 직원 수×시간(→ L) · 임대 규칙 · 원재료 인상률 u · 객단가 A · 일 주문 수 N.
- 식: `S = A × N × 영업일` (S 를 직접 움직이면 N 이 따라 움직인다 — 둘 중 마지막에 만진 것이 기준) · 원가율 `f' = f × (1+u) × (1+w)` · 수수료 `v = Σ채널비중×수수료율` · 공헌이익률 `c' = 1 − d − f' − v` · `영업이익(S) = c'·S − L − rent(S) − 로열티(S) − 기타`.
- **손익분기(임대가 max 규칙일 때)**: S* = R0 ÷ r (고정과 %가 같아지는 매출). 고정비 F = L + 기타. ① S ≤ S*: BEP₁ = (F + R0) ÷ (c' − 로열티율), 유효하면(BEP₁ ≤ S*) 답. ② 아니면 BEP₂ = F ÷ (c' − r − 로열티율), 유효(c' > r+로열티율 이고 BEP₂ > S*)면 답. 둘 다 아니면 «이 조건으론 흑자 불가».
- 표 출력: 매출 30k/40k/50k(+사용자 값) 예상 손익 · 손익분기 매출 · 하루 필요 주문 수 = BEP ÷ A ÷ 영업일 · 목표이익 T = F 를 F+T 로 바꿔 같은 식.

## 4. 데이터 구조 — 새 표 1개 + 칸 3개 + 설정 JSON 1칸 (새 목록·새 경로 없음)

> `TRADE_STRUCTURE` 규칙 대조: 재료·상품·가격에 새 목록을 만들지 않는다. 원가는 기존 2경로, 매출은 기존 정의. 여기서 새로 적는 것은 **매장 운영비(돈이 나가는 규칙)와 사람 단가** 뿐이다.

### 4-3. 설정 — `restaurants.operation_settings.profitability` (새 표 없음)

- 저장은 출퇴근 설정처럼 **전용 라우트가 읽어서 합친 뒤 통째로**(부분 저장 사고 메모리 · `guardOperationSettings`).

### 4-4. 모듈 — `profit_analysis`(Q4). 마이그 1개 `scripts/migrate-create-profitability.js`(표 CREATE IF NOT EXISTS + 칸 ADD IF NOT EXISTS + 모듈 등록, 멱등, 레지스트리 `deploy`). ENUM 은 새 표·새 칸이라 하드코딩 아님(기존 ENUM 변경 0).

## 6. UI/UX — «보기만 해도 알게» 의 규칙 6개와 화면 4개

### 6-1. 규칙(모든 화면 공통)
1. **숫자 하나에 판정 하나.** 큰 숫자 + 색 점(● 좋음 / ● 주의 / ● 나쁨 — 기존 danger `#EF4444`, 주의 `#F59E0B`, 좋음 `#10B981`) + 아래 작은 글씨 «왜» 한 줄(«원가율 38 % — 목표 35 % 보다 3 %p 높음»). 색만으로 말하지 않는다(글씨가 같이 간다).
2. **기준 없이 숫자 없음.** 모든 비율 옆에 비교값: 목표(설정) · 전 기간 · 브랜드 평균(브랜드 화면) 중 하나 이상. 추세는 ▲▼ 글리프 + %p.
3. **준비도 띠.** 페이지 맨 위에 «레시피 연결 72 % · 원가 아는 매출 88 % · 마지막 실사 10/03 · 시급 입력 5/7명 · 운영비 규칙 있음» — 없는 것은 그 자리에서 **바로 가기 버튼**(레시피 관리 / 실사 / 직원 / 설정). 데이터가 없을 때 빈 화면을 보여 주지 않고 **다음 행동**을 보여 준다(기획 글 «입력을 복잡하게 만들면 실패» 의 화면 쪽 답).
4. **추정은 추정이라고 쓴다.** «판매 당시 원가» 가 없어 현재 원가로 채운 라인 비중, 장부 대신 이론으로 넣은 식재료비 등은 칸 라벨에 «추정» 꼬리표. 숨기면 그게 최악(검증 규율 4조).
5. **한 화면 = 한 질문.** 탭 이름이 질문이다: «어느 메뉴가 돈이 되나» / «이번 달 얼마 남았나» / «재료가 어디로 샜나» / «손님은 어떻게 시키나» / «매출이 바뀌면 어떻게 되나». 탭 안은 위에서 아래로 **결론 → 그래프 → 표** 순서.
6. RA 디자인 기준 그대로: `PageComponents`·`StatCard`·`DataTable`·`Button`·`Modal`·`DateRangeField`, 기하 글리프, 이모지 0, 인라인 hex 금지. 그래프는 `dataviz` 규칙(의미색만, 범례·축·툴팁 일관) — 막대·waterfall·4분면 산점도·히트맵 4종만 쓴다.

### 6-2. 화면 ① 매장 «Profitability»(RA · Owner 가 매장 고른 뒤) — `/pos/profitability`
- **머리**: 기간 선택(이번 달 기본, 전월·최근 12주) + 준비도 띠 + StatCard 6개: 순매출 · 공헌이익(률) · 식재료비율(실제/이론 표기) · 인건비율 · 프라임코스트율 · 영업이익(추정). 각 카드에 판정색·추세·«왜» 한 줄.
- **제안 칸(3단계부터)**: 카드 최대 3장 — «사실 → 추정 효과 → 가서 보기» 형식(§7).
- 탭 5개:
  - **메뉴** — 4분면 산점도(점 = 메뉴, 크기 = 매출, 색 = 분면, 호버 = 수량·공헌이익·률) + 오른쪽 분면별 행동 문구 + 아래 표(순위·메뉴·카테고리·판매가·수량·순매출·원가(현재/판매당시 토글)·공헌이익·률·분면). 원가 미등록 메뉴는 표 아래 «원가 미등록 n개 — 레시피 걸기» 묶음.
  - **손익** — waterfall(총매출 → 할인 → 순매출 → 식재료 → 수수료 → 공헌이익 → 인건비 → 임대 → 로열티 → 기타 → 영업이익) + 각 막대 아래 출처 라벨(장부/이론/규칙/입력) + 월별 추이 막대(최근 6개월 영업이익률).
  - **재료 차이** — 기존 FoodCostTab 을 여기로 옮기고(중복 화면 금지) 수량 눈금·사유 분해 추가: 재료별 가로 막대(이론 | 실제, 차이 %p 색) → 클릭하면 사유 분해(폐기 6종·만들기·조정·실사 차이) + «레시피에 없는 재료» 묶음.
  - **주문 구성** — 채널 9칸 표(주문·순매출·객단가·주문당 공헌이익·수수료) · 카테고리 동반주문률 가로 막대 · 옵션 추가율·세트 전환율 StatCard · 시간대 히트맵(매출 | 인건비율 두 줄, 2단계부터) · 조합 상위 10 표.
  - **시뮬레이터** — 왼쪽 손잡이 10개(슬라이더+숫자 입력, 기준값은 «최근 12주 실적» 으로 채워져 있고 되돌리기 버튼), 오른쪽 결과: 매출 구간 표(30k/40k/50k/내 값) · 손익분기 매출(큰 숫자) · 하루 필요 주문 · 목표이익 입력 → 필요 객단가×주문 수. 임대 규칙이 max 이면 손익분기 설명에 «매출 46,154 까지는 고정 6,000, 그 뒤 13 %» 한 줄.
  - **설정**(톱니 아이콘, 탭 아님) — 수수료율 표(결제수단별) · 목표(원가율·프라임코스트율·차이 경고 %) · 운영비 항목 표(추가/닫기, 규칙 3종 라디오) · 직원 단가(직원 관리 화면의 칸이지만 여기서도 바로 가기) · «브랜드와 손익 공유» 스위치(Q1).
- 폰 너비: StatCard 2열, 산점도는 표로 대체(터치로 분면 필터), waterfall 은 세로 목록.

### 6-3. 화면 ② Owner «Store Comparison» — `/pos/owner/profitability`
- 표 한 장: 행 = 매장, 열 = 순매출·공헌이익률·식재료비율·인건비율·프라임코스트율·영업이익률·준비도. 셀 배경 = 판정색(히트맵). 열 머리 클릭 정렬. 행 클릭 → 그 매장 화면 ①(as 매장 선택).

### 6-4. 화면 ③ Brand «Store Profitability» — `/pos/brand/general/profitability`
- 탭 «매장 비교» = 화면 ② 와 같은 표 + 브랜드 평균 행. 공유 안 켠 매장은 인건비·임대·영업이익 셀이 «—(매장이 공유 안 함)».
- 탭 «표준 원가 대비» — 행 = 브랜드 메뉴, 열 = 매장(히트맵): 셀 = 매장 원가 ÷ 브랜드 표준 원가 − 1(%). 10 % 넘게 비싼 매장 셀이 주의색 → «이 매장이 비싸게 사거나 레시피가 다르다» 의 입구. 마지막 열 = 브랜드 전체 분면(4분면 집계).
- 탭 «브랜드 판매» — 이미 있는 브랜드 판매 통계(`/api/brand/sales-report`)·프로덕트 마진(`productMargin`) 으로 가는 링크만. 새로 만들지 않는다.
- Brand Manager: 같은 화면, 돈 칸 가림(기존 `financial_redacted` 패턴).

### 6-5. 화면 ④ 제안 카드(3단계) — 별도 페이지 없음, ①②③ 머리에 끼움
카드 1장 = «사실(숫자·기간) → 추정 효과(RM/월) → 버튼(해당 탭·설정으로)». 예: «Bulgogi Beef 공헌이익이 4주 전보다 8 %p 내렸습니다(원가 9.50→11.20). RM1 인상 시 월 +RM 420 → 가격 보기». 카드는 하루 1회 계산·최대 3장·«무시» 가능(무시 기록은 `localStorage` 아님 — 설정 JSON `dismissed_insights[]` 에 코드+기간).

## 9. 입력 최소화 — 매장이 손으로 넣는 것은 다섯 가지뿐

## 10. 검증 설계(각 단계 gate 때 Fable 이 볼 것)
1. **diff 범위** — 보호파일 8개 지문 0 · 차감 서비스 0줄 · 매출 정의 0줄 · `menuUnitCosts` 는 «추가» 만(본체 결과가 바뀌면 FAIL).
2. **수학** — §3-10 12건 테스트 통과 + 고장주입 1회(수수료 배분을 빼면 사례 1 이 실패하는가).
3. **실호출** — 데모 매장 38 에 `[확인용]` 주문 3건(일반·100 % 할인·직원식사)과 레시피 걸린 메뉴 2개로 summary·menus·order-mix 값을 손계산과 대조. 오너·브랜드 범위 반증(§5).
4. **화면** — 폰·태블릿·PC 스크린샷으로 «숫자 하나에 판정 하나·준비도 띠·추정 꼬리표» 가 실제로 보이는가(ux 점검 1회).
5. **배포 안전** — 마이그 멱등 2회 실행 · 모듈 키 등록 · 롤백 = 표·칸 그대로 두고 라우트 마운트만 빼면 됨(데이터 손실 0).

- **푸드코트 역할 화면** — Irene 가 든 세 역할만. 서비스 함수는 같아서 다음에 라우트·화면만 더하면 된다.
- **새 재료·상품·가격 목록** — 0개(`TRADE_STRUCTURE` 규칙).

## 12. 열린 위험(Irene 결정 아님 — 구현 때 지킬 것)
- **데이터가 없으면 화면도 비어 보인다.** 그래서 준비도 띠(§6-1 ③)가 1단계 필수다 — 이게 빠지면 «기능이 안 된다» 로 보인다.
- **주문 라인 상품 해석**은 `resolveProductId` + 이름 보조(`reports-summary` 방식) 둘뿐. 세 번째 규칙을 만들면 그게 다음 사고다.
- **오너·브라우저 집계 화면**(`OwnerReportsPage`·`BrandReportsPage` 5,000건)은 이번에 손대지 않지만, 새 화면이 서버 집계로 가므로 두 숫자가 다를 수 있다 — 새 화면에 «수익성 화면은 서버 집계·직원식사 제외» 한 줄. 옛 화면 정리는 통계 미연동 건(메모리 `project_stats_figures_not_linked`)과 함께 별건.
- 운영 DB 의 레시피 연결률·실사 빈도를 보지 않았다(운영 접근은 Irene 몫). 1단계 배포 전 `운영검증` 에서 SELECT 로 세어 준비도의 현실을 보고한다.
