## 배포 스크립트

**사용할 스크립트: `/var/www/deploy-to-production.sh`**

### 🔴 미커밋 = 다른 방의 진행 중인 일 — 커밋하지 않고, 빼고 배포한다 (2026-10-11 Irene · Fable FABLE.md §7)

> Irene 원문: «배포를 하면 모든 작업 일시정지하고 점검 후 배포해야지. 진행중인 거 있으면 그건 빼고».

- **배포는 «마지막 커밋의 깨끗한 사본» 에서 나간다.** 스크립트가 `scripts/make-clean-source.sh` 로
  `git archive HEAD` 사본(`~/.cache/purplehere-deploy/deploy-clean`)을 만들고, 검사·프론트 빌드·백엔드 rsync·
  마이그 파일·배포 기록을 전부 그 사본에서 한다. 작업 폴더의 미커밋·미추적 파일은 **저절로 빠진다** —
  시작할 때 «미커밋 N개는 이번 배포에서 빠집니다» 와 목록을 찍는다.
- ⛔ **배포 방은 작업 폴더의 미커밋 변경을 커밋하지 않는다** — 그건 다른 방의 진행 중인 일이다.
  배포에 넣고 싶으면 그 일을 한 방이 끝내고 커밋해야 한다(«/개발완료»).
- ⛔ **stash·`git checkout`·`reset`·`mv` 로 작업 폴더를 비키지 않는다** — 더 필요 없다(예전 격리 방식은
  미커밋 9파일 영구 소실 사고가 있었다, 메모리 [[feedback_stash_before_deploy_isolation]]).
- 작업 폴더에서 운영으로 가는 것은 없다. 단 배포 기록 보관함 이동(`releases/*.json` → `archive/`)만 작업 폴더에서 한다.
- 새로 생긴 실패 하나: **커밋된 코드가 아직 커밋 안 된 파일을 부르면** 사본엔 그 파일이 없다. 프론트는 빌드가,
  백엔드는 게이트 4d(`check-relative-requires.js`)가 잡아 배포를 세운다 → 그 파일까지 커밋된 뒤 재배포.
- git 이 추적하지 않는 운영 파일(QZ 인쇄 서명 키 `config/qz-cert/private-key.pem` · `.env` · `backups/` 등)은
  rsync 보호 목록으로 넘겨 운영 것을 **보내지도 지우지도 않는다**.
- 배포 뒤 개발서버 화면은 «커밋된 상태» 번들이다(사본 빌드를 dev 에도 올려 mount sweep 이 운영 번들을 검사하므로).
  진행 중이던 방은 이어서 일할 때 자기 `build:dev` 로 다시 올리면 된다.
- `--skip-build` 는 없앴다(작업 폴더 build/ 에 미커밋이 섞일 수 있음).
- ⚠ 자동 저장(cron `auto-save.sh`, 30분 쉬면 wip 커밋)이 만든 커밋은 «커밋된 것» 이라 사본에 들어간다.

### 정기 점검의 배포 단계 = Irene 상시 지시 (2026-10-11)

> Irene 원문: «배포는 아침점검에서 자동으로 하는거야» · «처리된 업무들 전체 체크해서 알아서 배포하는 건 수동배포(버튼 누를 시) 또는 아침 점검 때야».

- **상황판 정기 점검(아침 점검)의 «배포» 단계는 `/배포` 지시와 같게 본다** — 따로 «배포할까요?» 묻지 않는다.
  조건(상황판이 확인): 개발완료 ✅ · 새 커밋 있음 · 검증 통과 · Fable 대기 0 · 배포와 얽힌 답 기다림 0.
- 정기 점검 배포는 **버전을 올리지 않고, 릴리즈 노트·업데이트 공지·메일을 하지 않는다** (아래 «배포 완료 후» 절의
  버전·릴리즈노트·블로그/공지 단계 생략. CHANGELOG `[Unreleased]` 는 그대로 둔다 — 다음 수동 배포에서 버전과 함께 정리).
- 실패하면 즉흥 롤백·재시도 금지 → ❌ + 상황판 맨 위에 되돌리는 명령 1줄(FABLE.md §7 6번).
- 자동 허락에 막히면 터미널 1줄(`! /var/www/deploy-to-production.sh --auto`)만 남긴다.

### 배포 단계

| 단계 | 작업 |
|------|------|
| 1 | SSH 연결 확인 (87.106.78.146) |
| 2 | 개발서버 헬스체크 (localhost:3001) |
| 2a | **깨끗한 사본 만들기** — 마지막 커밋(`git archive HEAD`) · 빠지는 미커밋 목록 표시 |
| 3 | **안전 게이트 (fail-closed)** — 사본 기준: print-guard·인쇄필드계약·디자인·하드코딩·IDOR·마이그 레지스트리·배포 마이그 실전(dev DB)·**사본에 없는 파일 require(4d)**·타임존·hydration·인쇄라우트·배포기록 / 작업 폴더 기준(살아 있는 dev): health-check·인스펙션 + 배포 델타 분류(check-sensitive-diff, 정보용) |
| 4 | 운영 DB 덤프 + 운영서버 백업 생성 |
| 5 | 프론트엔드 빌드 — **사본에서** `build:dev` (dev nginx 에도 올라감) |
| 6 | **post-build 게이트** — 실브라우저 mount sweep (verify-all --only mount, 크래시 0) = 운영에 갈 바로 그 번들 |
| 7 | rsync: **사본** dev-backend → 운영 production-backend (무시 파일 보호 목록 적용) |
| 8 | rsync: **사본** dev-frontend/build → 운영 production-frontend/build |
| 9 | 운영서버 npm install --production + DB sync + 마이그레이션(커밋된 레지스트리) |
| 10 | PM2 production-backend 재시작 |
| 11 | 운영서버 헬스체크 (localhost:3002) + Nginx 리로드 + 스모크 테스트 |
| 12 | **배포 스냅샷 기록** (`.claude/deploy-manifest.json` — **사본**의 지문 · 이후 배포 델타의 앵커) |

게이트 실패 = 배포 중단. 긴급 핫픽스 우회는 `--skip-safety` (의식적 선택, Irene 지시 시에만).

## 배포 완료 후 CHANGELOG 업데이트 + 버전 업데이트 + 릴리즈 노트 출력 + 블로그 포스트 자동 생성

> **정기 점검 배포에서는 이 절 전체를 하지 않는다** (버전·릴리즈노트·공지·메일 없음 — 위 «정기 점검의 배포 단계»).

### CHANGELOG.md 업데이트 (필수)

배포 성공 시 `/var/www/CHANGELOG.md`의 `[Unreleased]` 섹션 내용을 새 버전 섹션으로 이동:

1. `[Unreleased]` 아래 내용을 모두 복사
2. `[Unreleased]` 아래를 비우고 (섹션 헤더는 유지)
3. 바로 아래에 새 버전 섹션 생성: `## [vX.XX] — YYYY-MM-DD 배포`
4. 복사한 내용을 날짜 헤더 없이 (flat list로) 새 버전 아래에 붙여넣기
5. 릴리즈 노트 작성 시 이 내용을 그대로 참고

### 버전 업데이트 (Irene에게 확인)

배포가 성공하면 **Irene에게 버전을 올릴지 물어본다.**

질문: "버전 올릴까요? (현재 v3.4)"

- **올린다고 하면**: patch 버전 +1 → session-state.md, DEVELOPMENT_PLAN.md, CHANGELOG.md 반영 + 릴리즈 노트 출력
- **안 올린다고 하면**: 버전 유지, 릴리즈 노트 생략

버전은 **배포 시에만** 올린다. `/개발완료`에서는 버전을 변경하지 않는다.

### 릴리즈 노트 출력

**배포가 성공적으로 완료되면, 마지막에 반드시 왓츠앱용 릴리즈 노트를 생성하여 출력합니다.**

#### 작성 규칙
1. 이번 배포에 포함된 주요 변경사항을 **CHANGELOG.md의 새 버전 섹션**에서 수집 (1차 소스)
2. 추가로 DEVELOPMENT_PLAN.md와 git diff도 참고하여 누락 없는지 확인
3. 한글 + 영문 둘 다 작성
4. 왓츠앱에서 깔끔하게 보이도록 마크다운 리스트(-, *) 사용 금지
5. 이모지 넘버(1️⃣ 2️⃣ 3️⃣ 4️⃣)와 줄바꿈으로 구조화
6. 구분선은 `━━━━━━━━━━━━━━━━━━` 사용
7. **제목 형식: `📢 PurpleHere POS Update v{버전}`** (한글 제목 사용 금지)

### 릴리즈 콘텐츠 자동 등록 (랜딩 블로그 + System Admin 공지)

**버전을 올렸으면 반드시 실행.** 버전 미변경 시 생략.

배포가 성공하고 릴리즈 노트를 작성했다면, 같은 내용을 **두 곳에 동시 자동 등록**합니다:
1. **랜딩 페이지 블로그** — 영어 1개 포스트 (`updates` 카테고리)
2. **System Admin 공지** — 영어 + 한글 이중언어 공지 (`updates` 카테고리, target_type=all)

#### 실행 방법

1. 릴리즈 JSON 생성 — 랜딩은 영어, 공지는 영어/한글 동시 포함:

```json
{
  "version": "3.13",
  "date": "YYYY-MM-DD",
  "landing": {
    "title": "PurpleHere POS v3.13 Update",
    "content": "## What's New\n\n- Feature one: user-facing description\n- Feature two: ..."
  },
  "notice": {
    "title": "PurpleHere POS Update v3.13",
    "content_en": "1️⃣ Feature A\n\nDescription line\nSecond line\n\n2️⃣ Feature B\n\n...",
    "content_ko": "1️⃣ 기능 A\n\n설명 한 줄\n두 번째 줄\n\n2️⃣ 기능 B\n\n..."
  }
}
```

2. 스크립트 실행 (dev DB 생성 + 운영 DB 자동 동기화):
```bash
cat /tmp/release-v3.13.json | node /var/www/dev-backend/scripts/create-release-post.js --stdin --sync-prod
```

- `--stdin`: JSON을 stdin에서 읽음
- `--sync-prod`: SSH로 운영 DB 자동 동기화 (블로그 포스트 + 공지 + 수신자 생성 포함)

3. 결과 확인:
- 랜딩 블로그: `https://purplehere.com/news (업데이트 글은 /blog 가 아니라 /news 에 나옴)`
- System Admin 공지: 모든 역할의 공지 페이지에 노출됨 (target_type=all)

#### 콘텐츠 작성 가이드라인

**랜딩 블로그 (영어 단일):**
- 제목 형식: `PurpleHere POS v{version} Update`
- 내용: 사용자 친화적 영문. 마크다운 `##` 섹션 + `-` 리스트 사용 가능
- **기술 세부사항 제외**: 파일 경로, 함수명, 내부 변수 금지. 사용자가 체감하는 화면/기능 위주
- 고유명사 유지: PurpleHere, POS, QR 등 영문 그대로

**System Admin 공지 (이중언어):**
- 제목 형식: `PurpleHere POS Update v{version}` (영어)
- content_en / content_ko 각각 이모지 번호(1️⃣ 2️⃣ 3️⃣)와 줄바꿈으로 구조화
- 마크다운 리스트(`-`, `*`) 사용 금지 — WhatsApp 스타일 프리텍스트
- 스크립트가 자동으로 `content_en` + `━━━━━━━━━━━━━━━━━━` + `content_ko`로 결합하여 하나의 공지 content에 저장
- 기존 v3.12 공지 포맷 그대로 따름

#### 스크립트 동작 상세

- `updates` 카테고리는 최초 1회만 생성 (blog: `ContentCategory`, 공지: Notice.category ENUM)
- 블로그 slug 패턴: `release-v{version}` (예: `release-v3.13`)
- 재실행 시 동일 version이면 업데이트 (중복 생성 안 됨)
- 공지 수신자는 is_demo=false/is_test=false 인 모든 레스토랑 + 4개 역할(Admin/Brand/Foodcourt/Owner) 사용자 자동 생성
