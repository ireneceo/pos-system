# 운영서버 안전 배포

운영서버에 안전하게 배포하는 명령어입니다.

---

## 배포 프로세스

### 1단계: 사전 확인

1. **Git 상태 확인** - 커밋 안된 변경사항 확인
2. **마지막 배포 이후 변경된 파일 확인** - `.last-deployed-commit` 파일로 이전 배포 커밋과 비교
3. **변경 규모 분석** - 변경된 파일 수, 핵심 파일(orders.js, server.js 등) 변경 여부 확인
4. **프론트엔드 빌드 테스트** - `npm run build` 실행하여 빌드 에러 없는지 확인

### 2단계: 개발서버 핵심 기능 API 테스트 (필수!)

배포 전 개발서버(dev-backend, port 3001)에서 레스토랑 핵심 기능을 테스트합니다.
**하나라도 실패하면 배포를 중단**하고 문제를 해결해야 합니다.

#### 테스트 항목

| 테스트 | API | 성공 조건 |
|--------|-----|-----------|
| 서버 상태 | GET /api/health | `{"status":"ok"}` |
| 메뉴 조회 | GET /api/menu/:restaurantId | `success: true`, 메뉴 데이터 존재 |
| 카테고리 조회 | GET /api/categories?restaurant_id=:id | `success: true` |
| 주문 생성 | POST /api/orders | `success: true`, order_id 반환 |
| 주문 조회 | GET /api/orders/:orderId | `success: true` |
| 주문 결제 | PUT /api/orders/:orderId/payment | `success: true` |
| 주문 삭제 | DELETE /api/orders/:orderId | `success: true` |

#### 테스트 실행 방법

```bash
# 개발서버 API 테스트 (Claude가 자동 실행)
BASE_URL="http://localhost:3001/api"
TEST_RESTAURANT_ID=5  # 테스트용 레스토랑

# 1. 서버 상태
curl -s "$BASE_URL/health"

# 2. 메뉴 조회
curl -s "$BASE_URL/menu/$TEST_RESTAURANT_ID"

# 3. 카테고리 조회
curl -s "$BASE_URL/categories?restaurant_id=$TEST_RESTAURANT_ID"

# 4. 주문 생성 테스트 (테스트 후 삭제)
ORDER_RESULT=$(curl -s -X POST "$BASE_URL/orders" \
  -H "Content-Type: application/json" \
  -d '{
    "restaurant_id": '$TEST_RESTAURANT_ID',
    "order_type": "dine_in",
    "table_number": "TEST99",
    "items": [{"product_id": 1, "quantity": 1, "price": 10}],
    "total_amount": 10,
    "skipAutoMerge": true
  }')
ORDER_ID=$(echo $ORDER_RESULT | jq -r '.data.id // .order.id // empty')

# 5. 주문 조회
curl -s "$BASE_URL/orders/$ORDER_ID"

# 6. 주문 결제
curl -s -X PUT "$BASE_URL/orders/$ORDER_ID/payment" \
  -H "Content-Type: application/json" \
  -d '{"payment_method": "cash", "amount_paid": 10}'

# 7. 테스트 주문 삭제
curl -s -X DELETE "$BASE_URL/orders/$ORDER_ID"
```

#### 테스트 결과 판정

- **모두 성공**: 배포 진행
- **1개 이상 실패**: 배포 중단, 원인 분석 필요
- **서버 응답 없음**: PM2 상태 확인 후 재시작

### 3단계: DB 스키마 비교 (필수!)

**중요**: 배포 전 반드시 개발 DB와 운영 DB의 스키마를 비교해야 합니다.

```bash
# .env 파일에서 DB 정보 로드
source <(grep -E "^DB_" /var/www/dev-backend/.env | sed 's/^/export DEV_/')
source <(grep -E "^DB_" /var/www/production-backend/.env | sed 's/^/export PROD_/')

# 테이블 비교
mysql -u $DEV_DB_USER -p$DEV_DB_PASSWORD $DEV_DB_NAME -N -e "SHOW TABLES;" | sort > /tmp/dev_tables.txt
mysql -u $PROD_DB_USER -p$PROD_DB_PASSWORD $PROD_DB_NAME -N -e "SHOW TABLES;" | sort > /tmp/prod_tables.txt
comm -23 /tmp/dev_tables.txt /tmp/prod_tables.txt

# 주요 테이블 컬럼 비교 (products, restaurants 등)
for table in products categories restaurants users orders; do
  echo "=== $table ==="
  dev=$(mysql -u $DEV_DB_USER -p$DEV_DB_PASSWORD $DEV_DB_NAME -N -e "SELECT GROUP_CONCAT(COLUMN_NAME ORDER BY ORDINAL_POSITION) FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='$DEV_DB_NAME' AND TABLE_NAME='$table';" 2>/dev/null)
  prod=$(mysql -u $PROD_DB_USER -p$PROD_DB_PASSWORD $PROD_DB_NAME -N -e "SELECT GROUP_CONCAT(COLUMN_NAME ORDER BY ORDINAL_POSITION) FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='$PROD_DB_NAME' AND TABLE_NAME='$table';" 2>/dev/null)
  comm -23 <(echo "$dev" | tr ',' '\n' | sort) <(echo "$prod" | tr ',' '\n' | sort)
done
```

누락된 테이블이나 컬럼이 있으면 **반드시 먼저 추가**한 후 배포하세요!

### 4단계: 변경사항 확인 및 커밋

배포될 변경사항 목록을 사용자에게 보여주고, 커밋 안된 것이 있으면 커밋합니다.

### 5단계: 배포 실행

**중요**: 반드시 `sudo`로 실행해야 합니다 (nginx reload 권한 필요)

```bash
echo '7u7LnxNr' | sudo -S /var/www/deploy-production.sh
```

배포 스크립트가 자동으로 .env 백업/복원, DB 백업, 코드 동기화, 빌드, PM2 재시작을 수행합니다.

### 6단계: 배포 검증

배포 완료 후 반드시 다음을 확인합니다:

1. **배포된 커밋 확인**: `.last-deployed-commit` 파일의 커밋이 현재 HEAD와 일치하는지 확인
2. **프론트엔드 빌드 파일 확인**: `production-frontend/build/static/js/main.*.js` 파일의 타임스탬프가 방금 생성되었는지 확인
3. **PM2 서버 상태 확인**: `pm2 list | grep production`으로 서버가 online 상태인지 확인
4. **API 테스트**: 메뉴, POS 터미널 등 주요 기능 동작 확인
5. **DB 설정값 확인**: 배포 후 currency, rounding 설정이 유지되는지 확인

### 7단계: 운영서버 핵심 기능 테스트 (배포 후)

배포 완료 후 운영서버(production-backend, port 3002)에서도 동일한 핵심 기능 테스트를 실행합니다.

```bash
BASE_URL="http://localhost:3002/api"
TEST_RESTAURANT_ID=8  # 운영 테스트용 레스토랑

# 동일한 테스트 실행 (주문 생성/삭제 테스트는 선택적)
curl -s "$BASE_URL/health"
curl -s "$BASE_URL/menu/$TEST_RESTAURANT_ID" | jq '.success'
curl -s "$BASE_URL/categories?restaurant_id=$TEST_RESTAURANT_ID" | jq '.success'
```

**실패 시**: 즉시 롤백 실행 (`sudo /var/www/rollback-production.sh`)

## 필수 체크 항목

### 배포 전 반드시 확인:
- [ ] 마지막 배포 이후 변경된 파일 목록 확인
- [ ] 의도한 변경사항이 모두 포함되어 있는지 확인
- [ ] **개발서버 핵심 기능 API 테스트 통과** (2단계)
- [ ] **개발 DB와 운영 DB 스키마 비교 완료**
- [ ] **누락된 테이블/컬럼 운영 DB에 추가 완료**
- [ ] 프론트엔드 빌드 성공 확인
- [ ] 커밋 안된 변경사항 커밋 완료

### 배포 후 반드시 확인:
- [ ] `.last-deployed-commit`가 현재 HEAD와 일치
- [ ] `production-frontend/build/` 파일 타임스탬프가 최신
- [ ] PM2 production-backend가 online 상태
- [ ] **운영서버 핵심 기능 API 테스트 통과** (7단계)
- [ ] https://purplehere.com 접속 정상
- [ ] **POS 터미널 메뉴 표시 정상**
- [ ] **API 에러 없음 (pm2 logs로 확인)**
- [ ] Settings > Currency 설정값 유지 확인

## 검증 명령어 (수동 확인용)

```bash
# 1. 배포된 커밋 확인
cat /var/www/.last-deployed-commit
git rev-parse HEAD

# 2. 프론트엔드 빌드 시간 확인
ls -la /var/www/production-frontend/build/static/js/main.*.js

# 3. PM2 상태 확인
pm2 list | grep production

# 4. 백엔드 로그 확인 (에러 확인)
pm2 logs production-backend --lines 20

# 5. API 테스트
curl -s http://localhost:3002/api/health

# 6. DB 설정값 확인
source <(grep -E "^DB_" /var/www/production-backend/.env | sed 's/^/export /')
mysql -u $DB_USER -p$DB_PASSWORD -e "SELECT currency, cash_rounding, rounding_apply_to FROM restaurants WHERE id = 8;" $DB_NAME
```

## 주의사항

- **sudo 필수**: 배포 스크립트는 반드시 sudo로 실행해야 nginx reload가 동작합니다
- **DB 스키마 비교 필수**: 배포 전 반드시 개발/운영 DB 스키마를 비교하세요
- **DB 설정 보호**: `sync-database.js`는 `alter: false`로 설정되어 있어 기존 설정값이 리셋되지 않습니다
- **롤백**: `sudo /var/www/rollback-production.sh [타임스탬프]`

## 관련 파일
- `/var/www/DEPLOYMENT.md` - 상세 배포 가이드

- `/var/www/.last-deployed-commit` - 마지막 배포 커밋 기록
- `/var/www/.deployignore` - 배포 제외 파일 목록
