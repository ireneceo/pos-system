# 검증 명령어

구현 완료 후 반드시 실행하는 검증 프로세스.
모든 단계를 실제로 실행해야 하며 확인했습니다만 말하는 것은 금지.
각 파트별 전문가 관점에서 체크하고 실제 결과를 보여줘야 한다.

## 검증 체계: 5개 파트 전문가 관점

개발기획: 요구사항 충족, 데이터 흐름 정합성, 엣지케이스 (3단계, 6단계)
백엔드 개발: API 정상, DB 정합성, 보안, 에러 처리 (2단계, 3단계)
프론트엔드 개발: 빌드, 타입 에러, 렌더링, 상태 관리, 상태 hydration 안전성 (1단계, 4단계, 0단계)
UI/UX 기획 디자인: 디자인 통일성, 인터랙션, 빈 상태, 로딩 (8단계)
QA: 유저 흐름, 역할별, 반응형, 연관 영향 (5단계, 7단계, 9단계)

## 10단계 검증 (건너뛰기 절대 금지)

0단계 정적 분석 (state hydration safety):
  `node dev-frontend/scripts/state-hydration-check.js` (working tree 변경 검사)
  또는 `--range HEAD~1..HEAD` (특정 commit 검사)
  새 state field가 생기면 모든 hydration source(localStorage, JSON.parse, fetch)에서
  defensive merge가 되는지, 모든 accessor(.length/.map/.filter 등)가 (... || []) 또는 ?.를
  쓰는지 자동 검사. 1건이라도 warning 나오면 다음 단계 진행 금지.

0-b단계 타임존 일관성 가드 (모든 시간은 매장 설정 타임존 기준 — Irene 확정):
  `cd dev-backend && node scripts/timezone-check.js`
  서버-로컬 today(`setHours(0,0,0,0)`) / timeZone 누락 `toLocale*` 를 잡는다. baseline(기존
  위반 추적) 모드라 **신규 위반이 0건이어야 통과**(exit 0). 신규 뜨면 → 백엔드는
  `getTodayBounds(getRestaurantTimezone(restaurant))`, 프론트는 `formatDateTime/formatDate`
  (utils/dateFormat) 로 교체. 기존 baseline 251건은 영역별 점진 교체 대상. 정식 통일분은
  `--bless` 로 baseline 갱신.

0-c단계 인쇄 라우트 가드 (자동인쇄 방식×프린터 회귀 — 인쇄 생명선, 인쇄/설정 인접 변경 시 필수):
  `cd dev-frontend && node scripts/print-route-guard/run.js` (게이트용 `--quiet`)
  utils/billPrint.js 자동인쇄 디스패치를 21루트로 **실제 실행**해 각 조합이 올바른 트랜스포트·
  프린터로 가는지(유령출력/누락 0) 검증한다. 축: 방식(browser/qztray-이름/qztray-LAN-IP/rawbt)
  × 프린터(빌/단일주방/멀티스테이션) × native앱/웹 × 매수/비상모드. qz-tray 를 기록용 스파이로
  바꿔 종이 직전 트랜스포트까지 관찰(종이 물리출력만 실기기 확인). 배포 게이트 7/7 과 동일 스크립트.
  신규 실패 뜨면 → 해당 라우트 수정. **정식 라우팅 변경이면** scripts/print-route-guard/cases.js
  기대값도 함께 갱신(피드백 1건 = 루트 1개). 단일 진실 = [[reference_kitchen_print_pipeline]].

1단계 빌드: npm run build:dev (run_in_background), 타입에러 0건 확인
2단계 백엔드: pm2 restart, 에러로그 확인, 인증/응답형식 체크
3단계 API 실호출: Node 스크립트로 실제 HTTP 호출. Write->Read 왕복, 에러케이스, 권한별 접근
4단계 프론트 렌더링: curl로 HTML/JS 번들 확인
5단계 유저 흐름: 역할별 로그인->기능->저장->재조회 순서대로 API 호출
6단계 요구사항 대조: 요청 항목별 구현 완료 여부 표시
7단계 연관 영향: 공통 컴포넌트 사용처 확인, 부작용 없음 확인
8단계 UI/UX 품질: 트렌디/고퀄리티 디자인 + 기능 적합성 디테일 점검
  8-A 디자인 시스템 준수:
    - 색상: UI_DESIGN_GUIDE.md 팔레트 일치 (#635BFF primary, #0A2540 text, #6B7C93 subtle, #E6EBF1 border)
    - 폰트: 크기 계층 (14px body / 12px label / 20px title), font-weight 500/600 일관
    - 간격: 8의 배수 (8/12/16/20/24/28), Section padding 24-28px
    - Border radius: 6px(input) / 8px(card) / 12px(section) / 16-20px(badge)
    - 절대 금지: 인라인 hex 색상 남발, 임의 px 간격, 커스텀 shadow
  8-B 트렌드/고퀄리티 디테일:
    - 마이크로 인터랙션: hover opacity, focus ring (box-shadow 0 0 0 3px rgba(99,91,255,0.1)), transition 0.15s
    - 스위치/토글: 라벨+힌트 조합, disabled 상태 opacity 0.5
    - 빈 상태 디자인: 단순 "No data" 금지 → 아이콘/설명/CTA 버튼 구성
    - 로딩 상태: spinner/skeleton, 갑작스런 레이아웃 변동(CLS) 없음
    - 에러 상태: 빨간 배지만 금지 → 설명 + 해결 힌트
    - 폼 저장: AutoSave 적용 여부, 저장 중 표시는 스위치 위 오버레이 (밖으로 튀지 않게)
    - 긍정 피드백: alert/toast.success 금지, 모달 닫기 + 자연 리프레시
  8-C 기능 적합성:
    - 필드 타입 최적화: 날짜는 DateField/DateRangeField (input type=date 금지), 금액은 CurrencyInput, 퍼센트는 PercentInput
    - 타임존: toLocaleString/DateString/TimeString 사용 시 timeZone 옵션 포함 (운영 레스토랑 기준)
    - 긴 폼: 4개 이상 섹션이면 탭/스텝 분할, 1개 화면 스크롤 과다 금지
    - 동적 리스트: +Add / 삭제 아이콘, 빈 배열 CTA 버튼, 카운트 배지
    - 체크리스트/설정: 그룹핑 + 카테고리 헤더, 12개 이상은 반드시 그룹화
    - read-only 모드: Input disabled 대신 definition list(dl/dt/dd) 고려, "—" 플레이스홀더
  8-D 반응형:
    - @media (max-width: 768px) 분기 확인: grid 1fr, padding 감소, 테이블→카드 변환
    - 가로 스크롤 발생 없음, 탭 overflow-x:auto 처리
    - 모바일 입력 UX: 키보드 타입 (inputMode numeric 등), 터치 타겟 44px+
  8-E i18n:
    - 하드코딩 텍스트 없음 (모든 문구 t('ns:key') 사용)
    - 4개 언어(en/ko/zh/ms) 키 존재 확인 `npm run i18n:verify`
    - fallback 문자열 자연스러움 (Placeholder/Error 포함)
  8-F 접근성 기본:
    - button에 type="button", 아이콘 버튼 title/aria-label
    - 토글은 role="switch" aria-checked
    - 색상 대비 AA 수준, 포커스 ring 표시
  8-G 실제 확인 방법 (필수 — 코드 리뷰만 금지):
    - 변경 페이지의 HTML을 curl로 서빙 확인
    - 구체적 파일:라인 인용하며 위 체크 항목 대조
    - 부적합 발견 시 즉시 수정 후 재빌드 → 재검증
9단계 크로스페이지: 네비게이션, SPA 라우팅, 역할별 리다이렉트

10단계 운영 critical 페이지 실 브라우저 mount 검증 (필수 — build 통과 ≠ runtime 안전):
  - **build / lint / type check / state-hydration / health-check 모두 통과해도 runtime 안전 X**
  - TDZ (Temporal Dead Zone) / hydration error / SSR mismatch / lazy chunk 초기화 순서 등은 정적 분석으로 못 잡음
  - 운영 critical 페이지 변경 시 **실 브라우저 mount 의무**:
    POS Terminal / 모바일 메뉴 / KDS / Floor Plan / 결제 흐름 / 매장 설정
  - 검증 방법: Playwright headless 자동 (`scripts/headless-page-sweep.js` 또는 신규 spec)
    실 브라우저 진입 → 진입 즉시 크래시 0 + `console.error` 0 + ErrorBoundary fallback 0
  - **purplehere v3.37 운영 critical 사례** (2026-05-22): TDZ 크래시로 매장 모바일 메뉴 차단.
    state-hydration 0 warning + health-check 80/80 + build success 다 통과 — 실 브라우저 mount 안 해서 못 잡음

11단계 (옵션, `--e2e`) Multi-step UI 자동 회귀 검증:
  - 사용 시점: 큰 변경 (UI 흐름 추가/변경, 신규 페이지, 결제 흐름 변경)
  - 핵심 시나리오 6개 (purplehere 맞춤):

    c) POS Terminal — 주문 + sandbox 결제 + 영수증
    d) Floor Plan zone — zone filter chip + 테이블 클릭
    e) Settings zones & groups — zone/group CRUD + table QR 생성
    f) KDS 자동 진입 — 결제 후 키친 ticket 자동 표시
  - **Flaky rate 100% 요구** — 3회 연속 돌려 100% 통과 안 되면 retry/wait 강화. 95% 기준 X (false negative 매장 신뢰 손상)
  - screenshot/trace 자동 보관: `/tmp/e2e/{YYYYMMDD-HHMMSS}/`
  - **LLM auto-fix 범위 — selector / waitFor / locator timing 만**.
    절대 금지: assertion text 변경 / network mock drift 자동 수정 / 비즈니스 로직 변경
  - **결제 sandbox 만**: Stripe test card (4242 4242 4242 4242), PayPal sandbox.
    운영 webhook URL e2e 절대 금지
  - **운영 데이터 e2e 절대 금지**: demo restaurant (dev: id=38 demo-korean-bbq) 만 사용
  - **운영 매장 영향 가드**: e2e 실행 전 token user 의 restaurant_id 가 demo 인지 확인

## 절대 금지
코드 확인만으로 정상이라 하지 말고 실제 호출 결과를 보여라.
API 호출 없이 검증 완료 금지. 빌드 안 돌리고 빌드 성공 금지.
에러 있는데 완료 금지. UI/UX 건너뛰기 금지.
0단계 hydration warning 무시 금지 — runtime crash로 이어진다.

## State Hydration 안전 패턴 (0단계 통과를 위한 가이드)

새 state field 추가 시 4가지 위치 모두 점검:

1. **useState 기본값**: 안전한 기본값 (`[]`, `''`, `0`, `null` 등) 명시
2. **DB load setState**: API 응답에 필드가 없을 수 있으므로 `Array.isArray(x) ? x : []` 패턴
3. **localStorage / JSON.parse setState**: 옛 캐시엔 필드가 없을 수 있으므로
   - 함수형 업데이트 `setX(prev => ({ ...prev, ...parsed, field: parsed.field || default }))`
   - 절대 `setX(parsed)` 형태로 통째로 덮어쓰지 말 것
4. **JSX 접근**: 모든 `.length` / `.map` / `.filter` / `.includes` 등을 `(state.field || []).method()` 또는 `state.field?.method()` 로 감쌀 것

위 4개 중 하나라도 빠지면 legacy 사용자에게 runtime crash. 0단계 스크립트가 모든 패턴을 검사한다.
