# /기능설계 — 대규모 신규 기능 설계 스킬

대규모 신규 기능/시스템을 **6단계 구조화된 설계**로 진행하는 스킬.
각 단계 완료 시 Irene 승인을 받고 다음 단계로 진행. 최종 산출물은 `/var/www/docs/` 폴더에 저장.

---

## 이 스킬을 언제 쓰나

**쓰는 경우 (대규모 신규 시스템):**
- 신규 DB 모델 3개 이상
- 신규 라우트 파일 여러 개
- 역할별 UI 페이지 추가
- 외부 연동, 결제, 이메일 파이프라인 등

**쓰지 않는 경우 (작/중 규모):**
- 버그 수정, 텍스트 변경
- 단일 기능 추가/수정
- CLAUDE.md의 "규모별 자동 조절" 표에서 `소`/`중`으로 분류되는 작업
- 이럴 땐 기존 CLAUDE.md 워크플로우(요구사항 → UX → 기술 설계 → 구현 → 검증)로 충분

---

## 6단계 설계 흐름

### 1단계: 기능 정의 (Feature Definition)

**산출물:** 이 단계에서 대화로 아래 항목 정리 + Irene 승인

| 항목 | 내용 |
|------|------|
| 기능명 | 한 줄 요약 |
| 목적 | 왜 필요한가 |
| 핵심 사용자 | 어느 역할이 쓰는가 (System Admin / Brand General / Restaurant Admin 등) |
| 핵심 유스케이스 | 3~5개 구체적 시나리오 |
| 기존 시스템과의 관계 | 어떤 기존 기능과 엮이는가, 어디까지가 범위인가 |
| 성공 기준 | "무엇이 가능해지면 완료인가" |
| 비범위 | 이 기능에 안 넣을 것 (명확히 선 긋기) |

**완료 조건:** Irene이 "이 방향 맞다" 확인

---

### 2단계: API 구조 설계

**산출물:** `docs/<FEATURE_NAME>_DESIGN.md`의 "API Endpoints" 섹션

| 항목 | 형식 |
|------|------|
| 엔드포인트 | `METHOD /api/path` |
| 역할 | 이 API를 누가 호출하는가 |
| 인증/권한 | `authenticateToken` + `requireRole(...)` + `checkRestaurantAccess?` |
| 요청 Body | 필드명, 타입, 필수 여부 |
| 응답 | `{ success, data }` 또는 `{ success: false, message }` |
| 에러 케이스 | 400/401/403/404 각 상황 |

**규칙:**
- CLAUDE.md의 API 응답 형식 표준 준수 (`{ success, data }`)
- 보안 체크리스트 적용 (3단계 미들웨어)
- `restaurant_id` 파라미터 신뢰 금지 → `checkRestaurantAccess` 필수
- 기존 라우트 파일 중 어느 파일에 넣을지 지정 (또는 신규 파일명)

**완료 조건:** 엔드포인트 목록 + 각각의 요청/응답 spec 확정, Irene 승인

---

### 3단계: DB 구조 정의

**산출물:** `docs/<FEATURE_NAME>_DESIGN.md`의 "Database Schema" 섹션

| 항목 | 형식 |
|------|------|
| 테이블명 | snake_case, 복수형 |
| 컬럼 | name / type / null / default / FK / 설명 |
| 인덱스 | 쿼리 패턴 기반 |
| ENUM | 값 목록 + 향후 확장 가능성 |
| 관계 | 1:N, N:M 명시 + 어느 테이블이 주인 |
| Sequelize 모델 | 파일명 + `models/index.js` association 추가 계획 |
| 마이그레이션 | `sync-database.js` 또는 수동 ALTER 계획 |

**규칙:**
- MySQL 64-key 한도 주의 (인덱스 과다 방지)
- `owner_user_id` 등 cross-tenant 격리 컬럼 검토 (brand scope, foodcourt scope)
- ENUM 추가 시 → 모델 파일 + ALTER TABLE 쿼리 모두 계획
- Soft delete (`deleted_at`) vs hard delete 결정

**완료 조건:** 전체 스키마 확정, `sync-database.js` 전략 결정, Irene 승인

---

### 4단계: UI 흐름 정의

**산출물:** `docs/<FEATURE_NAME>_DESIGN.md`의 "UI Flow" 섹션

| 항목 | 내용 |
|------|------|
| 페이지 목록 | 역할별 페이지 (List / Detail / Form 등) |
| 사이드바 메뉴 | `MainLayout.tsx` 어디에 추가, 아이콘, 순서 |
| 라우트 | `App.tsx`의 `React.lazy` import + path |
| ProtectedRoute | 역할 가드 |
| 페이지별 상태 | 주요 `useState` + 데이터 소스 (API) |
| 모달 | Create / Edit / Delete Confirm — 어느 페이지에서 쓰는가 |
| 빈 상태 | 데이터 0건일 때 화면 |
| 로딩/에러 | 스켈레톤, 에러 배너 |
| 반응형 | 모바일 대응 필요 여부 |
| i18n | 4개 언어 키 추가할 namespace |

**규칙:**
- UI_DESIGN_GUIDE.md 준수 (alert 금지, 성공메시지 금지, 이모지 금지)
- 기존 공통 컴포넌트 재사용 (`DataTable`, `Modal`, `Button`, `FilterBar` 등)
- 파일 크기 기준 (컴포넌트 800줄+ 분할)
- 설정 페이지는 `AutoSaveField` 패턴 검토

**완료 조건:** 페이지 목록 + 주요 화면 와이어프레임(텍스트 설명) 확정, Irene 승인

### 5단계: 코드 생성

**산출물:** 실제 구현 파일들

| 순서 | 작업 |
|------|------|
| 5-1 | 모델 파일 생성 + `models/index.js` association + export |
| 5-2 | `sync-database.js` 실행 또는 ALTER TABLE 실행 |
| 5-3 | 라우트 파일 생성 (보안 미들웨어 포함) |
| 5-4 | `server.js`에 라우트 등록 |
| 5-5 | 프론트 인터페이스 (`interfaces/`) 생성 |
| 5-6 | API 클라이언트 함수 (해당되면) |
| 5-7 | 페이지 컴포넌트 생성 (4단계 설계대로) |
| 5-8 | 사이드바 메뉴 추가 (`MainLayout.tsx`) |
| 5-9 | 라우트 등록 (`App.tsx`) |
| 5-10 | `ProtectedRoute`에 역할 가드 추가 |
| 5-11 | i18n 4개 언어 번역 파일 추가 |
| 5-12 | 이메일 템플릿 (해당되면) |

**규칙:**
- 2단계 API spec에 명시된 필드명/타입 엄격 준수
- 3단계 스키마에 명시된 컬럼명/타입 엄격 준수
- 4단계 UI 설계에 없는 컴포넌트 임의 추가 금지
- 각 파일 완료 후 Irene에게 간단히 보고

**완료 조건:** 빌드 성공 + 타입에러 0건 + health-check 통과

### 6단계: 테스트 시나리오

**산출물:** `docs/<FEATURE_NAME>_TESTS.md` + 실제 검증 스크립트

| 항목 | 내용 |
|------|------|
| 정상 흐름 시나리오 | 역할별 Write → Read → Update → Delete 왕복 |
| 권한 테스트 | 다른 역할/tenant의 데이터 접근 시도 (모두 403/404 기대) |
| 경계 케이스 | 0값, null, 빈 문자열, 최대 길이, 중복 |
| 에러 케이스 | 필수 필드 누락, 잘못된 타입, 존재하지 않는 FK |
| 이메일 알림 | 발송 여부 + 브랜딩/fallback 검증 |
| i18n | 4개 언어 각각 UI 확인 |
| 반응형 | 데스크톱/태블릿/모바일 각 화면 |
| 연관 영향 | 수정한 공통 컴포넌트가 다른 페이지에 영향 없는지 |
| health-check 확장 | 새 라우트에 대한 regression test 추가 |

**구현:**
- `dev-backend/test-<feature>.js` 임시 스크립트로 API 레벨 Write→Read→Update→Delete 검증
- 실제 로그인 토큰 → 실제 HTTP 호출 → DB 직접 조회로 결과 확인 → 스크립트 삭제
- `/검증` 스킬의 10단계 검증 전부 실행

**완료 조건:** 모든 시나리오 통과 + health-check 40/40 + `/검증` 10단계 통과

## 설계 문서 저장 위치

```
/var/www/docs/<FEATURE_NAME>_DESIGN.md   # 1~4단계 산출물
/var/www/docs/<FEATURE_NAME>_TESTS.md    # 6단계 산출물
```

**문서 작성 규칙 (CLAUDE.md의 기존 규칙 준수):**
- 기존 문서가 있으면 추가, 새 파일 만들지 않기
- 1문서 = 1주제
- 새 파일 만들기 전 `docs/` 폴더 확인

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

## 절대 금지

- 1~4단계 생략하고 바로 코딩 시작
- 설계에 없는 기능 임의 추가 ("김에 이것도 같이…")
- 한 단계에서 Irene 승인 안 받고 다음 단계로 넘어감
- 6단계 테스트 건너뛰고 "완료" 보고
- 작은 작업에 이 스킬 사용 (오버헤드)
