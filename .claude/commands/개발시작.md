## 절대 규칙: 운영서버 직접 수정 금지

### ❌ 절대 하지 말아야 할 것:

1. **샘플/가짜 데이터 사용 금지** ⭐ 매우 중요
   - 하드코딩된 샘플 데이터 (`sampleData`, `mockData`, `dummyData`) 사용 금지
   - 모든 데이터는 반드시 DB에서 API를 통해 가져와야 함
   - 테스트용 데이터가 필요하면 실제 DB에 추가할 것
   - 빈 데이터 상태는 빈 배열 `[]` 또는 Empty State UI로 처리
   ```javascript
   // ❌ 절대 금지
   const sampleData = [{ id: 1, name: 'Test' }];
   setData(sampleData);

   // ✅ 올바른 방법
   const response = await fetch('/api/data');
   const data = await response.json();
   setData(data.success ? data.data : []);
   ```

2. **운영서버 코드/설정 직접 수정 금지**
   - `/var/www/production-backend/` 디렉토리의 코드 수정 금지
   - `/var/www/production-frontend/` 디렉토리의 파일 수정 금지
   - `/etc/nginx/sites-available/purplehere.com` 설정 수정 금지
   - 운영 데이터베이스 (`purple_production_db`) 직접 수정 금지

2. **운영서버는 배포 스크립트로만 업데이트**
   - ✅ `/var/www/deploy-production.sh` 사용
   - ✅ 배포 가이드: `/var/www/DEPLOYMENT.md` 참조

3. **긴급 상황 시 대응**
   - PM2 재시작만 허용: `pm2 restart production-backend`
   - 서비스 상태 확인: `pm2 status`, `pm2 logs production-backend`
   - 설정/코드 수정이 필요하면 **반드시 개발서버에서 작업 후 배포**

## ✅ **올바른 개발 워크플로우**

### 1. 개발서버에서 작업
```bash
# 개발 디렉토리
/var/www/dev-backend/      # 백엔드 개발
/var/www/dev-frontend/     # 프론트엔드 개발

# 개발 데이터베이스
purple_dev_db              # 개발용 MySQL DB
```

### 2. 프론트엔드 빌드 (매우 중요!)

**⚠️ 절대 `npm run build`를 직접 사용하지 마세요!**

```bash
# ✅ 올바른 빌드 방법 (반드시 이 스크립트 사용)
cd /var/www/dev-frontend
./deploy-dev.sh

# ❌ 잘못된 방법 (index.html 누락 문제 발생)
npm run build
```

**왜 `deploy-dev.sh`를 사용해야 하나요?**
1. eslint 캐시 권한 문제 방지
2. `index.html` 생성 확인
3. 파일 권한 자동 설정
4. 빌드 실패 시 명확한 에러 메시지

**빌드 실패 시 (index.html 없음, 500 에러):**
```bash
# 캐시 삭제 후 재빌드
sudo rm -rf /var/www/dev-frontend/node_modules/.cache
cd /var/www/dev-frontend && ./deploy-dev.sh
```

### 3. 테스트 및 검증
```bash
# 개발 서버 접속
https://dev.purplehere.com

# 백엔드 포트: 3001 (개발)
# 프론트엔드: dev-frontend/build
```

### 4. DB 스키마 동기화 (매우 중요!)
```bash
# ⚠️ 새로운 테이블/컬럼 추가 시 반드시 수행!

# 1. 개발 DB에서 스키마 변경 테스트
cd /var/www/dev-backend
node sync-database.js

# 2. 개발 서버에서 충분히 테스트

# 3. 운영 배포 전 운영 DB 스키마 확인
# 배포 스크립트가 자동으로 처리하지만,
# 큰 변경사항은 사전에 확인 필요
```

### 5. 운영 배포
```bash
# 개발 완료 후 배포
/var/www/deploy-production.sh

# 또는
운영서버배포
deploy-prod
```

**배포 스크립트가 자동으로 하는 일:**
1. Git Pull
2. **운영 DB 백업** (자동)
3. 백엔드 코드 백업
4. 프론트엔드 빌드 백업
5. 코드 동기화 (dev → production)
6. npm install (운영 환경)
7. **DB 스키마 동기화** (Sequelize alter 모드)
8. 프론트엔드 빌드
9. PM2 재시작
10. Nginx 재시작

## 🔒 **DB 스키마 변경 안전 가이드**

### ⚠️ 반드시 지켜야 할 규칙:

1. **개발 DB에서 먼저 테스트**
   ```bash
   # 개발 환경에서 스키마 변경
   cd /var/www/dev-backend
   node sync-database.js

   # 서버 재시작 후 테스트
   pm2 restart dev-backend
   ```

2. **Sequelize 모델 변경 후 동기화**
   ```bash
   # models/ 디렉토리에서 모델 수정
   # 예: models/Recipe.js 추가

   # 동기화 스크립트 실행
   node sync-database.js
   ```

3. **운영 배포는 항상 백업 포함**
   - 배포 스크립트가 자동으로 DB 백업
   - 백업 위치: `/var/www/backups/[타임스탬프]/`

4. **롤백 준비**
   ```bash
   # 문제 발생 시 롤백
   /var/www/rollback-production.sh [타임스탬프]

   # 또는
   운영서버롤백 20251120_143000
   ```

### ✅ 안전한 DB 변경 프로세스:

```bash
# Step 1: 개발 DB에서 모델 추가/변경
cd /var/www/dev-backend
vim models/NewModel.js

# Step 2: 개발 DB 동기화
node sync-database.js

# Step 3: 개발 서버 재시작 및 테스트
pm2 restart dev-backend
# https://dev.purplehere.com 에서 테스트

# Step 4: Git commit
git add models/
git commit -m "feat: Add NewModel for feature X"
git push

# Step 5: 운영 배포 (DB 자동 동기화 포함)
/var/www/deploy-production.sh
```

### ❌ 위험한 DB 변경:

1. **직접 SQL 실행 금지**
   ```bash
   # ❌ 절대 금지
   mysql -u prod_admin -p purple_production_db
   ALTER TABLE ... # 직접 수정 금지
   ```

2. **Sequelize sync force 금지**
   ```javascript
   // ❌ 절대 금지 (모든 데이터 삭제)
   sequelize.sync({ force: true })

   // ✅ 사용해야 하는 모드
   sequelize.sync({ alter: true })
   ```

3. **수동 테이블 삭제/변경 금지**
   - 항상 Sequelize 모델 기반으로 변경
   - 기존 데이터 보존 우선

### 기본 규칙

| 위치 | 컨벤션 | 예시 |
|------|--------|------|
| **DB 컬럼** | snake_case | `restaurant_id`, `order_type` |
| **JavaScript 변수** | camelCase | `restaurantId`, `orderType` |
| **API Route Params** | camelCase | `/restaurants/:restaurantId` |
| **API Query/Body** | 둘 다 지원 | 호환성 보장 |

### 핵심 ID 매핑

| DB Column | JavaScript | Route Param |
|-----------|------------|-------------|
| `restaurant_id` | `restaurantId` | `:restaurantId` |
| `user_id` | `userId` | `:userId` |
| `order_id` | `orderId` | `:orderId` |
| `manager_id` | `managerId` | `:managerId` |
| `product_id` | `productId` | `:productId` |
| `recipe_id` | `recipeId` | `:recipeId` |
| `ingredient_id` | `ingredientId` | `:ingredientId` |

### API 호환성 패턴 (백엔드)

```javascript
// GET - 둘 다 받기
const { restaurantId, restaurant_id } = req.query;
const finalRestaurantId = restaurantId || restaurant_id;

// POST - 둘 다 받기
const { restaurantId, restaurant_id } = req.body;
const finalRestaurantId = restaurantId || restaurant_id;

// DB 저장 시 snake_case
await Model.create({ restaurant_id: finalRestaurantId });
```

### 새 기능 개발 시 체크

- [ ] DB 컬럼: snake_case
- [ ] Route params: camelCase
- [ ] Query/Body: 둘 다 받도록 구현
- [ ] 응답: DB 형식 그대로 반환

### ActionButton 스타일 표준

**모든 카드/리스트 아이템의 액션 버튼에 적용:**

```typescript
const ActionButton = styled.button<{ variant?: 'primary' | 'secondary' | 'danger' }>`
  flex: 1;
  padding: 8px 12px;
  border-radius: 6px;          // ⚠️ 8px 아님
  font-size: 13px;
  font-weight: 500;            // ⚠️ 600 아님
  cursor: pointer;
  transition: all 0.15s;       // ⚠️ 0.2s 아님

  ${props => {
    switch (props.variant) {
      case 'primary':
        return \`
          background: #635BFF;
          color: white;
          border: 1px solid #635BFF;  // ⚠️ border 필수
          &:hover {
            background: #4F46E5;
            transform: translateY(-1px);  // ⚠️ transform 필수
          }
        \`;
      case 'danger':
        return \`
          background: #FEF2F2;
          border: 1px solid #EF4444;
          color: #EF4444;
          &:hover {
            background: #FEE2E2;
            transform: translateY(-1px);
          }
        \`;
      default:
        return \`
          background: #F8FAFC;
          border: 1px solid #E2E8F0;
          color: #475569;
          &:hover {
            background: #F1F5F9;
            transform: translateY(-1px);
          }
        \`;
    }
  }}
\`;
```

## 📊 대용량 리스트 성능 최적화

### 적용 기준

- **50개 이상**: Progressive Rendering 자동 적용 (Intersection Observer)
- **50개 미만**: 전체 렌더링 (오버헤드 없음)

### 현재 적용된 페이지

| 페이지 | 방식 | 비고 |
|--------|------|------|
| POS Terminal | Progressive (50개+) | 초기 40개, 추가 30개씩 |
| Menu Management | Progressive (50개+) | 초기 40개, 추가 30개씩 |
| Live Orders | 페이지네이션 | 50개/페이지 |
| Mobile Menu | API 페이지네이션 | 서버에서 페이징 |

### 새 페이지 개발 시

1. **테이블 형태** → 페이지네이션 UI (50개/페이지)
2. **그리드/카드 형태** → 50개 이상 예상되면 Progressive Rendering 구현
3. **API 대량 조회** → 서버 페이지네이션 고려
