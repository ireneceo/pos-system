## 2. 새로 확인한 결함 — S1 (필수)

**100% 할인인 구독을 다시 저장할 때마다 청구서가 잘못 바뀐다.** 구독 화면 저장은 늘 plan 칸을 같이 보내므로 저장할 때마다 sync 가 돈다.

실호출(전부 원복함):
- **(a) 지난 청구서를 하나씩 덮어 닫음** — user 6(열린 청구서 여러 장)에 같은 100% 저장을 한 번 더 → 이번엔 **461**(다른 청구서 · 49.00 / 51.94 · 기간 06-09~)이 «799 · 기간 03-18~ · paid 0» 로 덮여 닫힘. 462 와 똑같은 내용 두 장이 됨. 저장을 거듭하면 238 · 180 · 178 순으로 계속 내려감.
  - 원인: sync 는 «가장 최근 열린 청구서» 를 고른다. 전에는 닫히지 않아 늘 같은 한 장만 고쳤는데, 이제 닫히니 다음 저장이 그다음 옛 청구서를 집는다.
- **(b) 열린 것이 다 없어지면 저장마다 새 청구서** — user 154(열린 청구서 1장)에 화면과 같은 전체 칸으로 100% 저장 3번 → 501 닫힘 → **INV-261110002 · INV-261110003** 이 «paid · 0 · Fully discounted» 로 새로 생김(같은 기간 03 장).
  - 원인: 열린 것이 없으면 `no_pending` → 호출부가 `createInitialInvoice` → 만들자마자 닫음. 중복 막는 장치 없음.

운영 영향: Irene 이 K-DINE 브랜드에 100% 를 «다시 적용» 할 때마다 (a) 지난달 미결 청구서의 기간·금액이 현재 기간으로 덮이며 닫히거나 (b) 0원 청구서가 한 장씩 는다. 돈이 잘못 걷히지는 않지만 **청구 기록이 사실과 달라진다**(돈·주문 무결성 칸).

### 고칠 것 (Fable 지시 · 한 곳)
`services/subscriptionInvoiceService.js` `syncPendingInvoice` — 열린 청구서를 찾기 **전에**:
1. `data = await buildInvoiceData(subject)` 를 먼저 계산(지금은 찾은 뒤 계산).
2. `data.totalAmount <= 0`(받을 돈 없음)이고, 같은 주체 범위(지금 `where` 에서 status 만 뺀 조건)에 **`status='paid'` · `total_amount = 0` · `billing_period_start` 가 `data.subStart` 와 같은 날**(함수 안 기존 날짜 문자열 비교 그대로)인 구독 청구서가 이미 있으면 → `return { updated: null, reason: 'already_closed_free' }`.
3. 호출부(users.js · restaurants-crud.js)는 `no_pending` 일 때만 새로 만들므로 손대지 않는다.

이 밖의 것은 건드리지 않는다. «가장 최근 열린 청구서를 현재 구독으로 덮는» 기존 설계와 «결제 끝난 구독을 저장하면 새 청구서가 생기는» 기존 동작은 이 일 범위 밖(아래 4).

### S1 통과 기준 (실호출 · 데모/시험 계정 · 끝나고 원복)
1. user 154: 화면과 같은 전체 칸으로 100% 저장 3번 → 구독 청구서 **1장 그대로**(501 paid 0) · 새 청구서 0.
2. user 6: 100% 저장 2번 → **462 만** 닫힘 · 461 은 `pending_payment 51.94` 그대로.
3. 이어서 할인 none 저장 → 정가 `pending_payment` 새 청구서 1장(기존 동작 유지).
4. 반증: 2번 조건을 빼면 1번에서 청구서가 2장 이상이 되는지 1회.
가능하면 1번을 health-check 에 영구 사례로 추가(권고).
