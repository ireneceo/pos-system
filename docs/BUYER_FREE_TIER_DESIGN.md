## 1. 왜 이 방향인가 (구조 실측 근거)

| 실측 | 값 | 뜻 |
|---|---|---|
| 발주·공급업체 라우트의 요금제 문(`requireModule`) | **없음** | 무료 등급에서도 발주가 **구조 변경 없이** 열린다 |
| 재고·레시피·상품 라우트의 요금제 문 | **있음**(`requireRestaurantModule`) | 무료 등급 모듈에서 빼면 **자동으로 닫힌다** — 새 차단 코드 0 |
| 화면 주소별 요금제 문 | **있음**(`ProtectedRoute` `MODULE_GATED_ROUTES`) | 줄만 더하면 화면도 같이 막힌다 |
| 사이드바 메뉴 | 역할·직원권한만 봄(요금제 안 봄) | **여기만** 조건 한 줄 추가 필요 |
| 계약 신청 | 있음(`POST /supplier-contracts`, 종료도 있음) | 무료 등급이 공급업체와 계약을 맺는 길이 이미 있다 |
| 인보이스용 매장 정보 칸 | 있음(상호·법인명·사업자등록번호·세금번호·법인주소·연락처·통화) | 새 칸 신설 없이 **필수 입력**만 걸면 된다 |
| 0원 요금제 선례 | 있음(오너 3종) · 화면은 0원을 «Free» 로 표기 | 요금제 표에 **줄 하나** 추가로 성립 |
| 발주 화면 모바일 | 1024px 이하에서 카드 + 하단 장바구니 시트 | 별도 «모바일 주문» 화면 **만들지 않는다** |

> 그래서 이 설계의 원칙은 하나다 — **새 역할·새 화면·새 주문 표를 만들지 않는다.**
> (CLAUDE.md 「기존 개념에 새 목록·경로를 만들지 않는다」 · 2026-08-28 Fable 결정 ⑤ 「구입권한 유저 = 신규 전역 역할 금지」와 같은 방향)

### 2-2. «발주 전후 연결되는 모든 기능» 의 범위 (Irene 지시 1)

들어가는 것: 공급업체 찾기·계약 신청/종료 · 외부 공급업체 직접 등록 · 상품 카탈로그 담기 · 발주 생성/제출/공유(왓츠앱·메일·PDF·인쇄) · 입고(전량/부분) · 반품 · 구입 청구서 · 인보이스 대조 · 결제 표시 · 발주 내역.
빠지는 것: 재고 수량 관리 · 레시피/원가 자동계산 · 메뉴/POS/주방 · 리포트.

> 경계 근거: 위 «들어가는 것» 중 요금제 문이 걸린 라우트는 없다(실측). 「빠지는 것」은 전부 요금제 문이 이미 지킨다.

### 2-3. 전환 유도 (Irene 지시 1)

- **발주 화면 안**: 담은 품목에 «이 재료의 원가·재고를 자동으로 계산하려면 → 레스토랑 관리자로 전환» 안내 1줄.
- **잠긴 메뉴**: 재고·레시피·업체관리를 **숨기지 말고 잠금 표시**로 보여 주고, 누르면 «무엇이 자동으로 되는지» 설명 + 요금제 변경으로 보낸다.
  (숨기면 있는 줄도 모른다 — 전환은 «보여 주고 막기» 가 맞다.)
- **입고 직후**: «입고하면 재고가 자동으로 늘어납니다 — 지금은 기록만 남습니다» 안내.

### 2-4. 인보이스 정보 필수 (Irene 지시 2)

> ⚠ 실측(2026-09-12): 매장 프로필의 법인명·사업자등록번호·세금번호는 **지금 서버가 강제하지 않는다**(있으면 저장, 없어도 통과).
> 발주 제출도 서버 필수는 «품목 1개 이상» 뿐이다. 따라서 아래 «발주 제출 전 필수»는 **이번에 새로 넣는 규칙**이며,
> §5-7 의 «필수 = 서버가 막는 것» 원칙에 맞추려면 **서버에도 같은 검사를 넣어야 한다**(화면만 막으면 규칙이 깨진다).
> 적용 범위는 **무료 발주 등급에 한정** — 기존 유료 매장의 발주를 새로 막지 않는다(운영 회귀 금지).

- 가입 시: 상호·연락처·주소(표준 `<AddressFields>`) — **필수**.
- 첫 발주 제출 전: 법인명·사업자등록번호·세금번호·법인주소 — **필수**(없으면 제출 버튼에서 프로필로 보낸다).
  왜 이 시점인가: 가입 문턱은 낮게, 문서가 필요한 순간(발주서·청구서가 상대에게 나가는 순간)에 받는다.

### 2-5. 공급업체·브랜드 «상품 보여주기 링크» (Irene 지시 3 · 축소판)

소비자 공개 가게는 **하지 않는다**(보류). 대신 B2B 유입용으로만:
- 공급업체/브랜드가 **카탈로그 링크**를 만들어 보낸다 → 열면 **상품과 가격을 보기만** 가능(담기·주문 없음).
- «주문하려면 무료 가입» 버튼 → 가입 후 그 공급업체와 **계약 신청**이 자동으로 걸린 상태로 발주 화면에 도착.
- 열쇠: 공급업체는 이미 있는 `supplier_companies.shop_slug` 를 재사용(값 0건, 용도 미사용). 브랜드는 `brands.code` 를 쓰거나 같은 이름의 열쇠를 더한다 — **Irene 확인 필요**.
- 표시 규칙: 가격은 **그 상대에게 보여 줄 값만** 화이트리스트로 직렬화(도매·계약가 비노출). 2026-08-28 결정 ⑧ 그대로.

## 4. 검증 기준 (구현 시)

1. 무료 등급 계정이 **발주 전 과정**을 끝낼 수 있다(공급업체 등록 → 계약 신청 → 담기 → 제출 → 입고 → 구입 청구서).
2. 같은 계정이 재고·레시피·POS 주소를 직접 열면 **화면과 서버 양쪽에서 막힌다**(403 / 잠금 화면).
3. 법인 정보 없이 발주 제출이 **막힌다**.
4. 요금제를 유료로 올리면 **같은 계정·같은 데이터로** 재고·레시피가 열린다(데이터 이전 없음).
5. 고장주입: 요금제 모듈에서 발주를 빼면 무료 등급 발주가 실제로 막히는지(문이 살아 있는지) 1회 반증.

### 5-2. UI/UX 자체로 알게 (문구가 아니라 배치로)

- 무료 등급 사이드바는 **발주 묶음만 펼친 상태**로 시작하고, 재고·레시피·POS 는 **잠금 표시 + 흐린 색**으로 남긴다 — **숨기지 않는다**(있는 줄 알아야 전환한다).
- 잠긴 항목을 누르면 **그 기능이 실제로 해 주는 일 한 화면**(입고하면 재고가 늘고 레시피 원가가 다시 계산되는 그림) → «요금제 바꾸기».
- 전환 안내는 **발주를 처음 보낸 직후**와 **입고 직후**에만. 상시 배너 금지(광고처럼 보이면 무시된다).
- 인보이스 정보는 **발주 제출을 눌렀을 때** 빠진 칸만 모아 한 번에 받는다(가입 때 받지 않는다).

### 5-3. 발주 화면은 지금 것을 그대로 쓴다 (신규 화면 0)

실측: 담기(`/pos/purchase-orders/new`) · 보내기 전(`/staging`) · 목록 · 상세는 **이미 매장·브랜드·푸드코트·오너 공용**이고 내부에서 «구매자 종류»로만 갈린다(분기 15곳). 무료 등급도 **같은 화면**을 쓴다.
⛔ 무료 등급 전용 화면을 만들지 않는다. 달라지는 것은 **사이드바에 무엇이 보이는가**뿐이다.

### 5-4. 브랜드 상품의 판매 대상 — 선택지 한 줄 추가

현재(실측): `brand_products.distribution_mode` = `all`(내 모든 가맹점) · `specific_brands`(31) · `specific_restaurants`(1) · all(5).
**추가**: `external_buyers` — «가맹점 밖 거래처에도 판매». 켜면 그 상품이 **공급형 계약을 맺은 거래처의 상품 목록**에 뜬다.

### 5-5. 공급형 계약 = 있는 것을 쓴다 (새 표 0 · **폼 교체 0**)

> Irene 확인(2026-09-12): 「브랜드 프랜차이즈를 폼 바꾸는 거 아니지? 2가지 종류로 선택해서 계약하게 해야 하는 것 같은데」
> → **폼은 그대로 둔다.** 실측: 계약 상세 폼에 **이미 «계약 종류» 선택 상자가 있다**(`ContractDetail.tsx:1414`).
> 브랜드는 `franchise` · `license` · `master` · `direct` 중 고르게 돼 있고, 모델 `contract_type` 은 자유 문자열(varchar 50)이다.
> 할 일은 두 가지뿐:
> 1. 그 선택 상자에 **«공급형(Supply)» 한 줄 추가** — 라벨은 «가맹형 — 우리 브랜드로 영업» / «공급형 — 제품만 공급».
> 2. **새 계약을 만들 때 종류를 먼저 고르게 한다.** 지금은 브랜드면 `contract_type: 'franchise'` 가 자동으로 박힌다(`ContractManagementPage.tsx:212`) → «가맹형 / 공급형» 두 버튼으로 시작.
> 칸 구성·단계(`stage`)·상세 화면은 **무접촉**. 공급형에서 안 쓰는 칸(가맹비·로열티 등)은 숨기지 않고 비워 둔다 — 숨기면 «왜 없지»가 된다.


실측: `contracts` 에 **`contract_type`**(varchar — 현재 franchise 20·tenancy 14·standard 8 등)과 **`stage`**(proposal → contracting → setup → active → terminated/renewed/expired)가 이미 있다. 브랜드 «프랜차이즈 관리» 화면은 공용 `ContractManagementPage` 를 `entityType="brand"` 로 감싼 **10줄 껍데기**이고, 생성 시 `contract_type: 'franchise'` 를 넣는다.
→ **공급형 = `contract_type: 'supply'` 한 값.** 관리 화면에 **«가맹형 / 공급형» 구분 탭 1개**와 목록 조회 파라미터 한 줄만 더한다(같은 맥락에서 관리하되 따로 본다 = Irene 지시).
신청 흐름은 공급업체 계약(`POST /supplier-contracts` — 메시지 + 승인 시 결제조건)과 **같은 모양**으로 만든다: 구매자가 브랜드 상품 링크에서 «거래 신청» → 브랜드가 공급형 탭에서 승인.

### 5-6. 카탈로그 링크 — 공급업체와 브랜드 둘 다

- 브랜드: `brands` 에 같은 이름의 열쇠(`shop_slug`, UNIQUE) 추가. 생성 규칙은 매장 `slug` 와 동일(소문자·공백→하이픈·100자).

### 5-7. 폼 «필수» 표시 — 최소화하고 한 방식으로 (2026-09-12 Irene 지시)

> 원문: 「그리고 모든 폼들 필수랑 아닌 거 표시가 없어. 필수를 최소화하고 불편함 없게 하자.」

**실측(추측 아님)**
- 규칙은 **이미 있다** — `dev-frontend/UI_DESIGN_GUIDE.md` §4.4: 라벨 옆 빨간 `*` · 상단 부족 항목 배너 + 섹션 칩 · **저장 버튼은 막지 않고** 누르면 누락 칸으로 스크롤·하이라이트(2026-04-19 개정, disabled+툴팁은 폐기).
- 그런데 **구현이 갈려 있다**: 가입 화면은 자체 `RequiredStar`(로컬 styled), 계약 상세는 `Label required` (`::after`), 나머지는 표시 없음. 표시를 쓰는 파일 **5개** / 폼이 있는 파일 **약 178개**.
- **화면이 서버보다 더 요구하는 곳이 있다**: 브랜드 상품 화면은 `required` 4곳인데 서버가 실제로 막는 건 이름·단위 정도. 반대로 서버만 막고 화면엔 표시가 없는 칸도 있다(매장 생성의 관리자 이메일·아이디·이름).

**규칙 (이 묶음에서 확정)**
1. **필수의 기준은 서버다.** 화면 필수 = 서버가 400 으로 막는 칸만. 서버가 안 막으면 별표를 붙이지 않는다.
2. **표시는 공용 부품 한 곳**: `components/Form/FormComponents.tsx` 의 `FormLabel` 에 `required` 속성을 더해 `::after` 로 빨간 `*`. 화면마다 별표를 새로 만들지 않는다(로컬 `RequiredStar` 신규 금지, 기존 2곳은 그 부품으로 수렴).
3. **선택 칸은 표시하지 않는다.** 「선택」 배지를 따로 달지 않는다 — 별표 없는 것이 곧 선택이다(표시를 늘리면 더 복잡해진다).
4. **막지 않는다.** 저장·다음 버튼은 항상 활성. 누르면 첫 누락 칸으로 데려가고 그 칸만 빨갛게 표시(UI 가이드 §4.4 그대로).
5. **자동저장 폼**(설정·계약 상세)은 빈 값도 그대로 저장된다 — 여기서는 별표를 «아직 안 채운 칸» 표시로만 쓰고 저장을 막지 않는다.
6. **무료 발주 등급의 인보이스 정보**도 이 규칙을 따른다: 가입 때는 상호·연락처만, 법인 정보는 **발주 제출을 누른 시점**에 빠진 칸만 모아서 받는다.

**하는 일 (구현 시)**: 공용 `FormLabel` 확장 1곳 → 발주·공급업체·계약·상품·가입 폼의 필수 칸을 **서버 기준으로 다시 세어** 별표 정리 → 남는 별표는 제거. 화면별로 흩어진 로컬 별표는 공용 부품으로 교체.

## 6. Irene 확정 (2026-09-12) — 더 묻지 않는다

### 6-1. 매장 1곳 = 가입 1건

> 원문: 「이게 우리 구조잖아. 그치? … 여러 레스토랑 등록시켜서 발주시키게? 그러면 나중에 레스토랑으로 연동 어떻게 해?」

- 발주의 주체는 **매장**이고, 유료로 올릴 때 **그 매장이 그대로 올라가야** 데이터가 끊기지 않는다. 여러 지점을 한 계정에 묶으면 전환 때 매장을 쪼개야 한다.
- 지점이 여럿이면 **각각 가입**. 나중에 오너 계정으로 묶는 건 기존 «오너 매장 연결» 경로 그대로.
- (내가 물었던 이유 = 오너 다매장 구조 때문. 구조상 답이 하나뿐이므로 **재질문 금지.**)

### 6-2. 계약 필요 여부 = 판매자 «설정» (공급업체·브랜드 **같은 기준**)

> 원문: 「공급형이랑 공급업체랑 같아야 해. 기준이. 설정으로 열지 말지 결정해야 하는 거 아니야? 무조건 계약해야 판매하지 않는 경우도 많잖아.」

**지금(실측)**: 공급업체는 **계약 필수**(활성 계약이 있어야 카탈로그에 뜸 — `supplier-directory.js:586~`), 브랜드는 **가맹점에 자동 노출**. 기준이 서로 다르다.

**바꿀 것**: 판매자가 **스스로 고른다.** 새 표·새 칸 없이 이미 있는 JSON 설정에 키 하나.
- 자리: `supplier_companies.operation_settings` · `brands.operation_settings` (둘 다 이미 존재 · 같은 패턴)
- 키: `sales_access` = `contract_required`(계약 승인 후 판매 — 지금 공급업체 기본값) | `open`(계약 없이 바로 주문 가능)
- `open` 이면: 카탈로그 링크를 받은 사람이 **가입만 하면 바로 담고 주문**할 수 있다. 계약 행은 첫 주문 시 자동으로 만들어 두되(거래 이력·결제조건을 담을 자리) 승인 대기로 막지 않는다.
- `contract_required` 면: 지금처럼 **신청 → 승인 → 노출**.
- 화면: 공급업체 설정과 브랜드 설정에 **같은 문구의 스위치 한 개** — «계약을 맺은 곳에만 판매» / «누구나 주문 가능(가입만)».
- 브랜드의 가맹점(가맹형 계약)은 이 설정과 무관하게 지금처럼 자동 노출 — 설정은 **가맹점 밖 거래처**에만 적용된다.
